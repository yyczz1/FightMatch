推荐首版：**单写入者、不可变完整代际文件、独立提交封记、当前及前一完整代保留**。每项操作保存一个完整业务版本，不靠多个 Model 各自落盘。不引数据库、分布式事务或新依赖；Android 文件同步能力拟由平台 Adapter 经现有 Android 接入能力封装，具体可调用性仍须实施验证。

| 保证 | 精确定义及当前证据 |
| --- | --- |
| 逻辑完整性 | 恢复所得所有业务切片、结果和引用来自同一版本；从不拼接新库存与旧成长。本文协议推演，尚无实现测试。 |
| crash consistency | 单写入进程在任意保存步骤消失，OS／文件系统仍正常时，恢复提交前完整版本或提交后完整版本；不展示半个业务操作。重启应用的验收必须跨进程读取，不能只检查内存。 |
| 成功后的 durability | 返回 Completed 后，即使应用重启或设备掉电，也应恢复该次或更晚已提交版本，**不能仅因旧版完整就允许丢失已报告成功的操作**。这比上一行更强。 |
| 本稿的承诺边界 | durability 以 Adapter 已验证的数据同步、命名空间同步及存储设备遵守这些完成语义为前置；目前全为 NOT RUN。磁盘损坏、卸载／清数据、人为回滚、系统备份恢复旧资料、硬件违背同步语义不属于该保证。不能用本地协议检测“整个已成功后缀连同证据全被抹去”。 |

只支持进程崩溃恢复的托管文件 Adapter 可以用于相应测试，但不能在未获 SD00 明确收窄 H10 前冒充正式持久 Completed。所需能力不支持时，在开始新业务保存前返回 `RecoveryBlocked(StorageCapabilityUnavailable)`；写到提交点附近才发生故障则返回 CommitUnknown。这里不要求现在安装依赖或修改平台设置。

## 2. 小而可调用的 Interface

下列均为拟定语义；只暴露完整版本，不开放“先写背包”“单独写权益余额”等入口。

| 调用 | 输入／输出与拒绝条件 |
| --- | --- |
| `Commit(expectedHead, candidate)` | 输入 PlayerId、上一 CommitId／代际、完整只读候选、OperationId＋意图指纹及各方已验证结果。接纳时 M12 分配稳定 CommitId 并立即给 ticket，异步 completion 返回 Completed／SaveFailed／CommitUnknown。expectedHead 不符返回 StaleContext；另一未决提交返回 Busy；同操作不同意图为 OperationConflict。 |
| `Lookup(player, commitId?, operationId?)` | 至少一个键；两个键均给出时必须相互对应。返回已提交的原结果及 CommitId，或 ConfirmedNotCommitted、CommitUnknown、RecoveryBlocked。查不到内存缓存不等于未提交；先按第 5 节核对物理版本和持久索引。 |
| `Load(player)` | 返回最新物理完整版本、代际／CommitId／摘要、能力依据与诊断，交 M02 让各负责者验证；全部成功前只供恢复检查，不安装为可写 Model。返回 UnsupportedBinding／RecoveryBlocked 时保留原文件与诊断。空目录只有在明确创建新 PlayerId 流程中才可初始化，不从损坏猜新用户。 |
| `ReadRecoveryRequirements(player, explicitCreateIntent?, expectedEvidence?)` | 固定启动层调用；完整枚举与技术校验后给出共同RecoveryRequirements及其完整性依据，不实例化业务类型。区分明确无档、新建许可、有效当前提交、CommitUnknown、RecoveryBlocked；expectedEvidence过时返回StaleContext及重查原因。只是只读能力，不创建资料、不返回业务Completed，细节见第5.1节。 |
| `ReadCapabilities()` | 返回保存故障模型、支持的格式版本；广告稳定身份、关联、查询／重投／确认接收能力；网络及时间来源能力。能力描述含 Adapter／平台版本，不能填供应商未证实的“支持”。 |
| `StartAd(savedRequest)`／`ReconcileAd(savedRequest)` | 只接收已经 Completed 的 AdRequestId 及原始用途／对象／提交引用。前者开始接入，后者查询或接收重投；输出原始回执或 Pending／Unavailable／CannotReconcile，不输出“已复活”。 |
| `SendAnalysis(request)`／`ReadTime()` | 前者只传 AnalysisRequestId、ContextKey、绑定及分析快照；后者返回第 9 节显式时间资料。两者都不修改玩家业务事实。 |

Commit ticket 不表示成功；SaveGeneration 按已提交版本单调增长，CommitId 唯一定位一个完整候选并映射其代际，不把它当可回退的回合号。同候选重试沿用 ticket；已确定未提交而需重新组织不同候选时，必须由 M02 先结束原办理并重新确认，不能偷偷改 ticket 内容。M12 仅补入保存元数据及操作结果的 CommitId，不重算业务切片。

候选由最后已提交快照构造，持有只读数据；保存期间不可被 Model、回调或序列化线程修改。组织者先查永久 OperationId 记录再校验期望修订，保证历史成功操作即使当前修订更高也返回原结果；M12 的 expectedHead 检查是防止过时整档覆盖的最后一道检查。

## 3. 保存记录与生命周期

| 记录 | 同版本必须保存的内容／拥有者 |
| --- | --- |
| `SaveEnvelope` | 格式版本、PlayerId、SaveGeneration、CommitId、ParentCommitId、正文长度、内容摘要、业务切片版本、明确区分包级 ContentBinding 与整关 DefinitionBinding 的引用清单；r3将本代恢复要求段和自足提交技术索引置于此稳定可读封套，见第5.1节。格式版本与规则／配置版本分别判断。 |
| `BusinessSnapshot` | S01～S14 及 S17 中玩家持久业务部分：成长恢复、库存装配冻结及当前偏好、进度教学和多关挑战、活动尝试、权益与请求、基础／增益结算、已保存攻略及其适用证据、可恢复办理阶段。S15 只保存内容绑定／引用，不复制发布包正文；S16 草稿／制作验证证据留在 M11 工作区，不进玩家提交。动画或 UI 选择不作事实。 |
| `ActiveAttempt` | AttemptId、EntryBaseline、全部未来面绑定、当前完整局面、完整有效回退历史、每步原 ActionConditions、随机／PRD、贡献／消耗、锚点及 GrantId／UseId 引用；M06 产出。SceneRevision 和操作索引不随历史回退。 |
| `OperationRecord` | OperationId、规范化原意图／指纹、业务唯一键、原结果、原 CommitId、新修订及被后续回退的关联；按操作范围保存包级或整关绑定。记录原已提交输出；Superseded 是追加的现况，不改写原结果或重办操作。 |
| `CommitRecord` | CommitId、代际、父提交、完整候选摘要、所属操作列表。当前snapshot封套包含从初始化至当前的唯一自足提交索引；新代继承已确认条目并追加本代，父链和历史查询不依赖祖先物理文件。当前代的完整摘要只在封记中，避免自引用；业务OperationRecord仍在正文，不另复制一份提交权威。 |
| `EndReceipt` | AttemptId、结束方式、报告指纹、SettlementId／BonusId、原操作结果、最终有效 GrantId／UseId 及撤回关系、冻结处理结果；M07／M06／M08 交叉确认。不能仅留“本局结束=true”。 |
| `AdRequest / Fact / Grant / Use` | 原请求用途及完整对象、按用途范围选定的包级或整关绑定、回执稳定身份／核验依据、资格及准确使用链、原限额期间／占位、兑现操作结果。事实集合只追加或作显式核验处置，不能由战斗快照替换。 |
| `RewardBasis / BonusOffer` | 入场持久的基础奖励随机依据、规则／随机版本和 AttemptId；基础结算持久的 BaseReward、SettlementId、报价及倍率随机依据；倍率结果及 BonusId 由 M07 固定。 |

首版保留全部必要 OperationRecord／CommitRecord 和结束凭据；对重复查询仍应返回的原结果必须自足，不能只引用将被删的历史。删除大块战斗快照不等于删除这些记录。后续若索引长期增长需分段，另提设计及验收；不能静默加入“30 天后同 ID 可重办”。

活动尝试历史不按容量或回合数裁剪。关闭的联合提交先持久EndReceipt、有效使用及撤回关系和原结果，再清理不可回退的完整历史；GrantReady、待办报价／结算和旧依据必须保留。立即重来依H06撤回旧尝试有效局内UseId，不能因历史清理丢失对应可用机会；正常结束的实际使用仍保留已用记录。物理备份清理和业务撤回是两件事。

H05 例：最新状态含 g1/u1 已用及后来广告 g2；回退候选只让 M06 恢复战斗切片，M08 撤回准确 u1，其他切片取最新版本。候选仍含 g1／g2 两份完成事实、当前偏好和永久学习，发布新修订。使用／撤回都经过同一提交点，绝不先暴露恢复的角色再异步更新权益。

基础掉落的 seed／流域／算法版本必须已在入场完成记录中；首次抽取晚于该提交。增益依据可以从已持久的独立奖励根及 SettlementId／报价版本确定性派生，报价随基础结算持久，首次倍率抽取晚于该提交。具体 PRNG 由 SD01／SD06／SD08共同定，M12 只保证依据同存；不得临时用当前时间重播种。保存失败、进程重启、另造 OperationId 均重建同一业务结果，战斗随机流不因广告而前移。

## 4. 物理协议候选与成本

Android 推荐使用平台返回的应用内部文件目录下 `saves/<PlayerId>/`，只保存相对路径；不硬编码 `/data/...`。这是待实施的新保存位置设计，不迁移现有用户资料。Unity 2022.3 的 persistentDataPath 在 Android 通常来自 getExternalFilesDir，不应把 Windows Editor 同名能力等同于 Android 内部存储。[Unity 2022.3 文档](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Application-persistentDataPath.html)、[Android Context.getFilesDir](https://developer.android.com/reference/android/content/Context#getFilesDir())。

候选布局如下，路径名仅由 M12 已校验身份生成；全部阶段处于同一保存目录、同一文件系统。目录首次创建也须满足父目录同步条件，再开始接受正式提交。

```text
saves/<PlayerId>/
  g-<generation>-<commitId>.snapshot       不可变完整版本
  g-<generation>-<commitId>.commit         对应提交封记
  w-<commitId>.snapshot.tmp                唯一进行中的正文
  w-<commitId>.commit.tmp                  唯一进行中的封记
```

推荐 snapshot 使用有长度／版本的封套＋固定序列化规则的 UTF-8 JSON 正文＋SHA-256 校验；封记保存 PlayerId、代际、CommitId、ParentCommitId、snapshot 文件名／长度／摘要及自己的校验。摘要覆盖身份／版本与正文，读取先检查长度和摘要再解析业务；摘要用于发现损坏，不是防篡改签名。具体编码器能力与最大可读长度由实施包验证，不使用不透明对象反序列化。

| 方案 | 收益 | 成本与取舍 |
| --- | --- | --- |
| **推荐：完整代际＋封记** | 无覆盖当前文件、无 mutable current 指针；提交与暂存可分辨；回执丢失能查询；恢复一个自足版本。 | 每提交写完整正文，约两次文件同步＋两次目录同步及校验；保留两份完整版本，写入峰值约三份。需 Android 同步 Adapter。 |
| A/B 槽覆盖＋序号校验 | 文件数量固定，可少一个封记。 | 不保留封记时“准备完成”和“承诺提交”混合；覆盖非当前槽及故障后的代际选择更难审计；仍需数据与目录的耐久依据，File.Replace 并不消除该要求。首版不选。 |
| 不可变历史块＋完整清单／封记 | 已有历史只写一次，长局减少重复 I/O；清单可描述完整逻辑版本。 | 增加跨文件引用、保留根、块校验及垃圾回收协议；损坏恢复和旧规则绑定更复杂。完整快照测量不达标时再申请，不预先实现。 |

设永久资料及凭据为 P、每步完整战斗快照平均 B、活动历史 H，则单代大小约 `S=P+H×B`；首版单次写入／校验 O(S)，一局反复全写历史的累计量约 O(H²×B)，不能宣称长局零成本。当前＋前一代＋一个候选约占 3S 磁盘峰值，不保留每个物理代。候选复用只读历史前缀，序列化流式写入及摘要，避免再制造整份 byte[] 和双份历史深拷贝；依然存在 O(H×B) 必要历史内存。

实施前测 10／100／1000 步及压力递增样本的大小、峰值内存、写入延迟分位数和后台切换中断；这些是测量点，不是回合上限。达到存储不足时返回明确失败并保留当前完整状态，不自动删除活动历史或漏存动作。是否转分块协议依据 Android 实测再交 SD00，不把容量优化扩大为本轮实施。

### 4.1 写入顺序与两个完成点

1. M12 独占该 PlayerId 写入口，确认 expectedHead 与已加载头一致；重查去重索引，冻结候选，分配 ticket。只允许本应用一个业务写入者；检测到第二写入者／头分叉就停止，不合并存档。
2. 将完整封套写入唯一 snapshot.tmp，关闭前完成编码器／用户缓冲刷新及文件数据同步；校验精确长度与摘要。任何短写、空间不足、权限拒绝均不更新旧文件。失败时保留或后续清理这个未提交暂存，不宣布业务成功。
3. 将正文改名为本次唯一 `.snapshot`，完成保存目录同步，确保正文数据及最终名字已到要求的耐久范围。这里只准备候选；有正文而没有最终封记不能自动提升为提交。
4. 写 commit.tmp，校验并同步封记文件，再改名为唯一 `.commit`。**最终封记可见是恢复算法的提交判据**；从开始这一步的最终改名起，异常不能直接归为 SaveFailed。
5. 同步保存目录并核对新正文／封记；这是要求 durability 的 **Completed 回答门槛**。若封记可见但同步失败，可能已成提交，返回 CommitUnknown 并通过 Lookup 解析，禁止删除封记当作取消。
6. M02 在一个发布点安装完整新快照／索引，再发 UI 通知。通知丢失不影响已存结果。新代已确认后才可清理更老物理文件；清理失败只留下额外文件，不把已成功业务改为失败。

步骤 2／3 保持旧代不动，步骤 4 前只可能恢复旧代；步骤 4 后若封记完整则引用已先完成同步的完整正文，恢复新代，否则在声明的崩溃模型内恢复旧代。不存在“新库存已提交、经验仍在旧文件”的窗口。针对断电，此推导必须建立在 Adapter 的数据／命名空间顺序确实落到设备上，不能仅凭代码调用次序断言成立。

Android `Os.fsync`／`Os.rename` 文档提供自 API 21 的入口，但入口存在不证明所选路径／文件系统已满足本协议。AOSP 持久属性实现也明确区分 rename 可见性与父目录同步；这里仅借其说明目录项是独立耐久条件，不复制其损坏后删除策略。[Android Os](https://developer.android.com/reference/android/system/Os)、[AOSP 依据](https://android.googlesource.com/platform/system/core/+/android16-release/init/persistent_properties.cpp)。

`.NET FileStream.Flush(true)` 的文档描述刷新中间文件缓冲；这不构成 Unity 2022.3 Mono／IL2CPP 的实测，也没有替本协议同步父目录。[Microsoft 文档](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush)。不能以 FlushAsync 完成、关闭流、重命名成功、同进程回读或 Windows 测试代替 Android 断电证据。

## 5. 查询、恢复选择与保留

Load／Lookup 在同一排他恢复流程内完整枚举最终封记，从最大代际核对身份／格式、封记校验和正文长度／摘要；不靠修改时间选最新。最新完整snapshot封套中的自足 CommitRecord 索引验证父链：本代 ParentCommitId 必须指向索引中的上一已提交记录，更早父关系沿索引检查至初始化记录，**不要求打开或保留对应祖先文件**。物理当前与前一代是恢复副本，不是重建当前状态所需的日志链。

最新头有效时，文件名身份及代际已被其索引确认的旧代，即使正文／封记部分缺失或损坏，也只记为旧副本损坏／清理残片；不拿它重建当前资料，不因此回滚或阻止完整当前代加载。前一备份损坏须报告冗余降低，后续正常提交可形成健康前代。无法对应索引的其他最终封记、同代不同头、分叉，以及无法解释的较新封记仍为 RecoveryBlocked；不能把可能承载已成功操作的新证据归为旧垃圾。临时文件与无封记正文只作未决证据，不提供业务状态；枚举不完整则无法排除更高代，仍阻塞。

| 观察 | 返回与后续 |
| --- | --- |
| 原候选从未进入最终封记发布，已确认旧头有效且无它的封记 | SaveFailed，附 OS 错误；同进程保留冻结候选并用原 ticket 重试。跨进程按原 OperationId／持久随机依据重新办理，先确认未提交。 |
| 已触及封记发布，调用异常、超时或回答丢失 | CommitUnknown；冻结冲突写入，查原 CommitId／OperationId，不能生成新 ID 来绕过不确定性。 |
| 原提交在最新快照索引中或为最新有效封记，版本可校验 | 返回原 Completed；若前次未能完成耐久确认，先补齐文件／目录同步并复核，失败则仍 Unknown／Blocked，不凭“文件能读”回答强耐久成功。 |
| 原提交不存在，旧头完整且枚举／持久索引检查完整、没有较新未决封记 | ConfirmedNotCommitted；需要目录同步才能确认命名空间稳定的 Adapter 先完成该步。无完整证据时仍 Unknown，不能用 FileNotFound 单独推断。 |

| 最新物理版本可读但存档格式／业务切片版本不支持 | RecoveryBlocked(UnsupportedSaveVersion)，不忽略新文件选旧文件，不猜测字段默认值；本轮没有自动迁移。 |

加载快照后，M02 组织 M03～M09 检查冻结唯一对应活动尝试、消耗与学习、首通与奖励、有效 UseId 双向引用、报告与结束记录、操作索引、当前修订及所有必要绑定。校验失败时不得由 M12 补发物品、释放权益或清空记录“修复”。在尚未划定可独立安全继续范围前，默认停止业务写入，允许只读查看恢复诊断。

正常保留当前与紧邻前一已完成正文／封记；正在提交或 Unknown 时不清理。更老封记和正文只在最新已耐久且提交索引、必要原结果均已自足后删除；清理中断可能留下旧封记或旧正文单边残片，由当前索引识别，不影响当前加载。不会删当前／前一代，也不因索引含父引用而永久留祖先文件。初始化及维护也使用明确提交身份；备份保留不是自动回滚授权，外部事实无法从从未保存的字节中找回。

两种绑定已由SD00接收，定义唯一来源为共同契约第1节：ContentBinding用于局外学习／合成／用卡／装配、资源广告报价及局外恢复，无需LevelId，不填空值或伪造“当前关”；DefinitionBinding用于入场基线、活动尝试／历史、整关结算及增益、关卡教学、在线／默认攻略，包级绑定不能替代整关校验。

旧包保留根汇总两种绑定：当前／前一恢复代、Unknown 候选、活动入场／历史、未完成结算或广告报价、需要重新验证的已保存攻略，以及仍需旧依据的局外操作／恢复记录。由 M10 ResolveExact 按绑定类型提供原包与可执行规则兼容性，M12 不热换 V2；首版依 SD01 不自动裁剪包，未来备份和业务引用释放后才可提包清理，不能只看“当前关卡”。保存清单仅记录这些引用，不纳入发布包正文或制作草稿。

### 5.1 启动可读摘要与完整提交的关联

**最小落点：同一个snapshot的稳定封套，不新增摘要文件或current指针。** 固定层仅含长度受限、版本化的封套／封记读取、技术索引校验和流式哈希；业务正文为不透明字节，不反射业务类型、不初始化QFramework Model、不计算成长或战斗。正文摘要只散列业务正文，完整snapshot摘要只放在封记；封记自身校验排除校验字段，本代CommitRecord不存自身完整摘要，依赖没有环。

候选构造时，每个持久业务切片的唯一负责者同时交付该切片的不可变字节、版本和所需绑定／Rule／Numeric／Random能力声明；即使引用为空也必须明确声明。M02收齐所有实际切片，含待办广告／报价／结算、活动历史和需旧依据的恢复／延期效果。M12机械核对切片目录与声明一一覆盖、所属者与版本匹配、字节摘要一致、绑定字段完整，再取并集写本代要求段；少声明、重复或冲突则在写入前拒绝。不由M12搜索HP、奖励或角色字段猜引用；声明是否语义完整由负责者在候选校验及加载后复核负责，启动哈希不能证明业务声明正确。

第4.1节步骤2把本代要求段、唯一技术索引及正文写入同一snapshot.tmp；步骤3只取得准备好的snapshot；步骤4的封记同时绑定它们，步骤5仍是强持久Completed门槛。不存在“业务已完成，稍后补摘要”的步骤；要求段缺失／版本不支持时返回RecoveryBlocked，不从业务DLL临时推算、不初始化新资料。r2是设计稿而非已上线格式，本包不声称已迁移任何旧档；未来无该段的既存格式须另审恢复方案。

读取在M12保存／清理排他区间内取得一致证据，只阻止枚举期间的变更，不持锁等待下载。返回的完整性依据绑定当前CommitId／SaveGeneration、封记与snapshot摘要，以及每个有效备份／未决候选的身份、摘要或未知原因；它是本次枚举的只读证明，不是另一个可修改头。M14准备完成后，启用、代码回退或清理前带原依据重新调用；当前头不变但候选、备份或根集合变了也须StaleContext并重核对。最终核对与启用／清理授权在同一短排他边界，不能检查后允许一次新提交再执行旧授权；代码重启后仍重读。

启动阶段的Lookup只用稳定CommitRecord技术索引及封记核实提交身份与物理状态，物理未决解除后重读摘要，不解码业务OperationRecord或实例化热更类型。完整业务结果和业务意图终止由热更入口后办理；尚不能安全解决的候选根继续标未决，不能为了取得业务查询结果先启用未经核对的集合。

## 6. 业务队列与外部回调

M02 管一个业务写入队列；M07 的结算候选也走该队列。业务判断及切片发布顺序执行，文件 I/O 可在后台对冻结候选工作；此时可以读最后已提交视图，但冲突业务不执行。保存失败／Unknown 时保留原办理门闩；Lookup／恢复处理不排到一个永远被自身门闩挡住的普通攻击之后。

SDK／网络任意线程回调只复制最小不可变回执并投递消息；不直接修改 Model，不重入正在构造的候选。保存结果回到队列时，先完成该代发布，再用**最新**状态处理排队回执。队列不是永久日志：未持久回执可能随进程消失，其补录能力依第 7 节。保存阻塞时不得启动更多广告；已到回执在可持久前不谎称已核验保存。

分析与完整规则验证在独立快照上运行，不长期占业务队列。其结果归队后由 M09 检查 ContextKey；超时、旧页面、取消或对象关闭不删除已完成广告事实，也不阻止处理可核验旧回执。玩家的新攻击若当时 Busy，应由玩家后续再确认，不能被积压队列自动执行。

## 7. 广告 Adapter：先存请求，事实与效果分开

请求必须先完成保存：AdRequestId、PlayerId、用途、CharacterId／ChallengeId／AttemptId／SettlementId／报价与期间等准确对象、发起修订、按用途选定的内容绑定、原 OperationId、资源限额占位。局外资源广告和局外恢复用 ContentBinding；在线分析、局内复活、整关通关和结算增益用原对象的 DefinitionBinding。复活／恢复另保存原 CharacterId 及原 AttemptId／RecoveryId，不用 LevelId 冒充恢复期；后来换场不改原请求。StartAd 接受该提交引用后才接触 SDK；缺引用拒绝。SDK 不得凭“当前角色／当前页面”回写效果。

调用前后有不可消除的接入窗口：已保存请求但尚未调用，以及 SDK 已开始但本地未记录开始。重启先 ReconcileAd；只有 SDK 对该请求支持幂等开始或能证明从未开始，才可自动再调用。没有这种能力就保留 PendingExternal／CannotReconcile 并提示状态未知，不能自动再播广告，也不能伪造一次失败释放限额后再播。明确取消／失败且排除晚到完成的证据交 M08 决定释放；无凭据请求的后续处置由 SD07提出策略。

原始回执至少带 Adapter／供应商命名空间、稳定完成身份、原 AdRequestId 或可证明的映射、完成类型／证据、接收时间；M08 核验原请求与完成条件后生成唯一 AdFactId。一个请求最多一个逻辑事实；多次回调、不同回执编码或新 OperationId 都不能变成多份资格。不能仅用回调时间或随机 GUID 假装供应商稳定身份；SDK 只有单会话回调时只能保证本会话内关联。

| SDK 实际能力档案 | 可承诺行为 | 不可承诺与实施门槛 |
| --- | --- | --- |
| 稳定完成 ID＋原请求关联＋跨进程查询／重投 | 持久前丢回执可重新核验并补记；保存后重复回执被去重。 | 必须实测重启、延迟、重复、过期保留期与查询失败；仍不能假定无限保留。 |
| 上述能力另有“持久后确认接收” | 本地 Fact／GrantReady Completed 后才确认接收；确认丢失可重复确认。 | 必须证明 SDK 不会因尚未确认而另发一份权益，且确认语义确实存在。 |
| 稳定 ID／关联，但没有跨进程补录 | 当前收到后可防重；已保存事实可恢复。 | 广告完成到事实持久之间杀进程可能永久丢失资格；不能满足“每个真实完成必可找回”。 |
| 只有临时完成回调，无法稳定核验或关联 | 只能如实描述能力不足；不得拼凑原对象。 | 无法承诺跨进程准确补录；作为正式奖励接入需 SD00／SD07 接收明确限制或换具备所需能力的接入。此处不选供应商。 |

“可核验”使用经审核的 SDK 完成语义和其确实给出的证据，不虚称所有回调均有服务端签名。本地哈希不创造外部事实。未收到／未能补录核验事实时，页面残影、播放时长、网络成功、视频关闭都不能代替奖励完成。

事实保存`FactRecorded + GrantReady`后，兑现另作完整提交。复活／恢复归原CharacterId，增益归原SettlementId，资源归原报价及PeriodKey；在线保存原挑战与实际交付，未交付资格不能因挑战关闭销毁。通关保存原LevelId及发起AttemptId／ChallengeId，实际UseId另关联玩家选定的同关合法尝试B及其绑定；旧挑战结束不使未用资格失效，不自动用在当前场。效果与使用同存，关闭UI不回滚事实。

## 8. 网络传输限制

M12 只负责可用性检查、请求身份相关、传输／取消及原始结果；发出的是规则分析所需的隔离快照和明确资源前提，不是整份永久存档。网络返回候选、服务错误、超时、取消或不支持绑定；只有 M09 用同一 M06 规则完成验证后才能称 ValidatedWin，搜索失败不等于 ProvenNoSolution。发送前服务可用也不保证广告完成后仍可用；已得资格保留，失败可按原挑战免费重试。服务器响应不是玩家业务写入口，本设计不加入强制联网或远端存档。

## 9. 显式时间依据

`TimeSample = {WallUtc, MonotonicElapsed, MonotonicScopeId, Source, Trust, ObservedAt, Anomaly}`；保存上次接受样本与业务恢复身份／到期时刻，绝不只留剩余秒。Android elapsedRealtime 自开机计时且含休眠，但重启后不能延续比较；只有 Adapter 能证明同一时钟域才用单调差，不能自行假定进程重开等于同次开机。[Android SystemClock](https://developer.android.com/reference/android/os/SystemClock)。

推荐离线可用的本机时间作为明示来源；同一有效单调域用于间隔，跨域回退到带 `DeviceUntrusted` 标记的 UTC 样本。检测倒退／跳变并传出，不把来源标成服务器可信。M03 根据 RecoveryId、原到期时刻及样本计算自然恢复，非负且最多恢复到该业务期限完成；计算结果经 D01 保存，不使战斗中角色复活。墙钟前拨仍可能提前完成，这是本地离线策略的限制，不用强制联网掩盖。

资源广告 PeriodKey **只由 M08** 按发布的期间／时区策略及同一 TimeSample 计算，原请求持久绑定原期间；平台不在另一个账上算“今天剩几次”。建议倒退不重新开放已用期间，向前跳变记录异常；是否接受异常期间由 SD07 明示业务规则并交 SD00核对，不暗加次数限制。M03 的恢复和 M08 的限额分别消费时间依据，不各自调用本地日期产生互相矛盾的广告期间。

## 10. 故障矩阵与设计验收样例

以下是待执行断点和预期，**均非已通过测试**。每例以存储头 G、原操作 O、唯一候选 C 开始；故障恢复后先 Lookup，再检查完整业务状态及副作用次数。

| 断点／输入 | 期望恢复及可见结果 |
| --- | --- |
| 候选形成前；A10 用证学习／合成 | G 完整保留，不扣证／材料，不升级、不记已学；尚未确认的预览不变成待消费操作。 |
| snapshot 写入途中短写／空间不足／权限失败 | 无最终封记则已知 SaveFailed，G 不变；重试 O／C，随机依据不变，残片不可加载。若旧头也读不出则 Blocked。 |
| 正文改名后、提交封记改名前 | G 仍为业务头；孤立正文不算成功，也不触发 SDK 或通知。 |
| 封记发布点前／后杀进程 | 前恢复 G；后只有完整封记＋正文才取新代；异常先 Unknown。不是覆盖 current 文件，也不混合两代。 |
| 封记可见但目录同步失败／设备掉电 | 返回 Unknown，恢复补齐检查及同步；无能力依据不能声称强耐久 Completed。最新封记损坏不静默退 G。 |
| commit 已成但 completion／UI 通知丢失；A05／A10 | Lookup O／C 返回同已提交结果；学习、首证、基础奖励及增益各发一次。Completed 后重启／掉电应留该代或更晚代。 |
| 第一面最后操作／补线／救援；A03／A04 | 恢复同 AttemptId、面、AwaitLinks／AwaitRescue、完整历史与冻结 C；不把第一面当胜利，不返还、不重放敌方阶段。 |
| WonPendingSettlement；A05 | 恢复封闭报告及原奖励依据，先续办同 attempt 基础结算再允许新入场；不重抽掉落。广告通关无单独“资格已用待结算”暴露。 |
| GrantReady 尚未使用；A06 | 保留事实和准确原目标，效果尚未发生；按现状确认兑现，不假称已复活或已发增益。 |
| 使用／撤回途中；A03 | 旧完整“战斗旧状态＋原使用态”或新完整“战斗新状态＋对应使用变化”；g2 和当前偏好始终保留，重复撤回 u1 不释放后来 u2。 |
| 旧回调到达新尝试／新页面；A06 | 先记原事实；复活归原角色，增益归原结算。通关原尝试关闭或已正常通关时仍保留原关的一次未用机会，可在同关后续合法尝试手动用，不自动结束新场、不重复原奖励。 |
| 广告实际完成但进程未持久回执 | 有能力则按同请求补录且只一次；无查询／重投则 CannotReconcile，不凭时长发奖，不承诺必恢复。 |
| 活动历史裁剪请求／结束历史已裁剪 | 前者拒绝；后者从 EndReceipt／权益使用链判已花资格仍已用，旧 O 返回原结果，不凭历史为空退回机会。 |
| 新版内容发布、旧包缺失／旧规则不支持；A08 | 选择最新完整保存代，但受影响恢复为 UnsupportedBinding／RecoveryBlocked；保留旧绑定、历史、冻结，不热换 V2。 |
| 最新目标损坏／未知格式／两个同代头 | 保存证据并 Blocked；旧备份只能用于有审阅的恢复处置，不自动成为可花资源的当前档。 |
| 当前 G10 完整，G1～G8 已清理或留坏片，G9 为前一代 | 用 G10 自足索引检查历史父链并查询旧 O，无需 G1～G8 文件；已索引旧坏片只记诊断。若发现无法解释的 G11 最终封记则 Blocked，不将其当可清理残片。 |
| 无活动尝试时合成／局外资源广告／恢复，V1请求后发布V2 | 用原 ContentBinding、配方／报价／RecoveryId 及稳定操作身份保存和恢复，不生成 LevelId；缺 V1 阻塞受影响办理。玩家档只含绑定及业务资料，M11 草稿／制作验证证据不进入候选。 |
| 16首证已成而教学未完，中断后回刷；A09 | 首证与库存同代，学习门槛仍未完；关1和关16 Challenge 各存；再次加载不重赠、不封锁已合法返回路径。 |

未来实施验收分三层，先在独立临时测试资料上做，绝不直接故障注入真实用户档：

1. 普通 C# Interface 测试：对每个保存步骤注入短写、异常、重复查询与回调；序列化后重新创建 Module 加载，断言完整切片指纹、Operation／Commit 结果、唯一业务键和准确 UseId。并验证同 intent 重试、同 ID 不同 intent、回退后 g2 保留及固定奖励。
2. 真实文件／跨进程测试：独立 writer 到达每个断点后由测试控制进程结束，reader 新进程加载；覆盖清理中断、只剩孤立文件、最新损坏、旧版格式、磁盘满和同步失败。记录具体 OS／路径／文件系统／错误码；Windows 结果只代表 Windows，进程终止不冒充掉电。
3. Android 设备验收：授权构建后记录 Unity／后端／Android／设备／存储路径和 fsync／目录同步能力；分别做强杀应用、重启及可控掉电测试，核对每个已回答 Completed 的提交仍存在。同时验证 SDK 实际能力表、请求开始窗口、完成前后杀进程及重投。硬件测试给支持范围和观察结果，不宣传所有设备永久不丢数据。

本轮 **NOT RUN**：Unity 编译／EditMode、真实文件写入故障注入、跨进程保存、Android 构建／掉电、SDK／在线服务、性能测量。原因：仅获设计授权，未有本 Interface 实现或验证环境。现有 Unity 验证命令留在仓库规则中；后续任务明确测试程序集／过滤器及获授权设备步骤后执行，不在此捏造命令或测试数量。
