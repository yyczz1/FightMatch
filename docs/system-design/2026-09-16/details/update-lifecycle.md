## 1. 边界与完成对象

M14只有S19的修改权：发布集合、准备／启用阶段、本进程集合及启动失败。M12执行下载、文件校验、稳定摘要读取和加载接入；M10解释Published定义；M02在代码入口之后组织完整业务恢复。玩家当前头唯一来自M12，角色和战斗规则不进入固定启动层。

| 可观察阶段 | 能证明的完成对象 | 不能由此推断 |
| --- | --- | --- |
| 所需文件已取得 | 固定集合中本次依赖闭包的完整字节已取得并核验 | 发布可信、可执行或支持当前档。 |
| Prepared | 可信集合、必要代码／AOT／资源及初步兼容依据齐备 | 当前进程已换版本；依据仍可能过时。 |
| 启用已授权 | 本次启动目标与最新摘要通过最终核对并固定 | 代码已加载或玩家已可操作。 |
| CodeEntered | 对应集合代码加载、稳定入口握手成功 | 定义解析和全部玩家切片已恢复。 |
| BusinessReady | M10精确解析及M02完整恢复校验通过，报告准确CommitId和可操作范围 | 所有业务待办已经兑现，或所有远端章节已经下载。 |

这些是H11阶段，不新增一个降低H10保证的`Completed`。恢复中若需要续办结算、权益或其他写入，仍按原业务操作与H10办理；UI依据M02返回的实际可操作范围，不因CodeEntered放开战斗输入。

## 2. 最小内部关系与固定层

直接复用公共`ReleaseSetId / ReleaseCapabilities / RecoveryRequirements`，不再定义一个可独立修改的“游戏版本”。以下名称仅为M14内部记录角色，不承诺C#类型或磁盘格式。

| 内部资料 | 保存或持有的关系与寿命 |
| --- | --- |
| 集合目录 | 不可变发布描述及其指纹、可信验证依据、平台／基座要求、代码依赖图、必要AOT、资源目录、声明的内容绑定与能力。集合身份相同而字节不同一律拒绝。 |
| 准备记录 | 原OperationId、目标ReleaseSetId、所需内容范围、缺失／已核验文件、最近完整摘要依据和失败原因。下载断点是技术进度，不能成为可执行性证明。 |
| 启动记录 | 稳定操作身份、下次启动意图、被选集合及原成功集合引用、核对依据、启用／加载／入口／恢复阶段和诊断；仅S19设备资料，不保存玩家业务副本。 |
| 本进程运行句柄 | 完整加载后固定的ReleaseSetId与能力、加载状态、M10解析后的可用范围；进程内不更换代码身份。未准备入口时没有可供普通业务使用的句柄。 |

“下次启动目标”与“本进程已加载集合”必须分开：运行中登记R2重启意图，本进程仍为R1，M10的GetCurrentBinding仍校验R1。重启记录不是另一份玩家current指针，也不从它取得可写CommitId。

固定层只保留长度有界且版本化的启动记录／发布清单解析、可信验证、摘要比较、依赖加载、最小错误／进度界面和必要平台能力。不会静态引用热更业务类型、提前实例化业务System或序列化带热更脚本的首场景对象。主要UI、地图和战斗资源随匹配热更集合取得。

固定入口接收`ReleaseCapabilities`、恢复摘要依据、平台能力和受控加载结果，返回集合／入口协议握手及初始化失败；原始文件路径和SDK回调不成为业务写入口。入口协议版本属于集合对基座的能力要求，未知版本在执行前拒绝，不能先反射调用再猜兼容。

S19的小型启动记录由M12既有平台文件校验、原子发布和同步能力持久化，不另建业务保存系统。记录完整且耐久后才回答“重启意图已记录／启用已记录”；附近故障沿原操作查询，未知不宣布成功。物理原语及断点必须在实施任务验证，不能把托管写文件返回当耐久证据。启动记录损坏或版本未知保留现场并报告，不能据此清玩家档。

## 3. 对外Interface

M14对调用者隐藏下载任务、缓存目录与DLL装载次序，不要求M02逐文件协调。以下是语义接口提案；错误分类沿用共同契约，所有返回携操作对象与原输入指纹。

| 操作 | 输入→结果、顺序与拒绝 |
| --- | --- |
| `Prepare(operationId, targetSet, requiredScope)` | 固定目标集合和当前所需内容；读取摘要、验证发布与依赖，再异步取得缺失文件。返回Prepared及所据摘要，或进度／明确缺失／不兼容；不启用、不改变当前绑定。重复同意图续原目标，远端出现R3不把R2请求改写成R3。 |
| `RequestRestart(operationId, preparedSet, expectedRunningSet)` | M02传明确重启意图；当前集合不符为StaleContext。保存目标意图，协调当前H10已知完成及暂停新冲突操作后才进入可重启阶段；无须以战斗结束为前置，原活动尝试完整保留。未决提交先查原操作，不由M14取消。 |
| `Start()` | 固定层恢复S19、读取当前玩家摘要并重新核对目标，完成最终授权、代码加载及入口。返回CodeEntered或阻断原因；M02接续恢复后另回报BusinessReady。无档而无明确新建意图时只显示既定新建入口，M14不生成PlayerId。 |
| `EnsureContent(operationId, scope, expectedRunningSet)` | 仅取得当前已启用集合声明的内容依赖；核验后交M10解析。无需重启，结果只增加该集合已可用范围；缺声明返回LevelUnavailable，涉及新DLL／基座能力则必须另Prepare集合，不能偷换代码。 |
| `ReadStatus(operationId?)` | 给本进程集合、准备／重启阶段、可用内容范围和原因；重复查已记录阶段不重新执行。当前集合与待启用集合分列；加载失败不会被一次下载完成回调覆盖。 |

下载／查询可取消传输，已经核验的字节可以保留；取消不更改已记录启用阶段或玩家提交。不设置隐含强更倒计时；首次缺业务包只允许下载／重试，既有完整集合的普通离线业务不依赖更新服务可达。

## 4. 可信集合与兼容算法

发布信任与文件哈希分开检查。技术建议是由固定基座持有认可的验证根，对不可变发布描述及其引用文件清单验证授权，再核对内容字节；本包不选签名算法、密钥服务或部署商。仅HTTPS成功、缓存文件存在或哈希与同一个未受信清单一致，均不足以授权执行。

离线读取本机集合使用已取得的发布依据及本机验证能力，不新增每次启动联网许可。将来若引入密钥轮换、撤销或强更政策，须另审其离线影响；当前不以未设计的在线证书刷新否决已有完整集合。

准备算法按以下顺序进行，重复执行保持原目标；记录用于诊断而非跳过验证：

1. 从M12读取RecoveryRequirements。未知头、损坏摘要、不完整根或不支持格式，返回准确阻断；固定层可作技术Lookup后重读，不能解码热更OperationRecord、择旧档或补空摘要。
2. 校验目标描述的发布授权、不可变身份、平台／基座／入口要求。清单里的AOT必须指向当前应用基座与BuildTarget所需产物，不能替换成另一平台或另一次基座生成的“最新版”。原生库、引擎或AOT API缺失属于基座不支持，热更文件取得不能补出该能力。
3. 比较可读封套／切片版本与Rule／Numeric／Random执行能力；每个完整绑定必须在集合可提供范围中。只保留V1 JSON而仅能执行V2算法，比较失败；不把版本号大小当兼容。
4. 区分当前可执行头与备份／未决保留根，覆盖当前恢复所需闭包，并证明保留根仍有其所需包及执行能力可保留。备份仍不可作为当前业务；根不完整时不得启用或清理。M14核对声明，加载后各业务负责者再验证语义完整性。
5. 计算入口、必要代码／AOT、当前业务及当前所需关卡资源的依赖闭包。代码图必须无缺项／循环，按依赖序；一个集合中同一程序集身份只能映射一份确定字节。全量闭包不等于下载所有远端章节。
6. M12异步取得缺失文件至候选区，逐项验证长度／哈希及目录身份，禁止按URL最后文件名覆盖已用文件。所有必要项完整、持久且可重新核验后才登记Prepared；错误、空间不足或中断留原可用集合。

清单的能力声明还须有生产验证依据：确切基座构建、程序集／AOT产物身份、被支持旧版本的读档和规则见证。不由客户端现场运行制作测试，也不把声明的字符串本身当兼容已实测。本包不冻结Numeric／Random标准或替火球候选选择数值。

复杂度以文件／依赖／要求条目线性扫描及拓扑检查为目标；字节哈希和下载离开业务写入队列。缓存可按不可变指纹复用，但缓存索引不代替最终文件和引用根检查。无测量数据，不承诺冷启动秒数或内存上限。

## 5. 启动、重启和业务恢复

启动先恢复更新记录，优先使用明确重启意图指向的Prepared集合；没有新意图则核对上次成功的本机集合，不自动追随CDN最新。目标失败但尚未发生任何代码／AOT加载时，可重新核对原成功集合；只有它仍覆盖最新玩家摘要才可使用。

1. 固定层完成长耗时文件／信任／能力检查，取得准备依据。M12在保存／清理短排他区间内重读摘要，比较当前CommitId、有效备份、所有未决候选及根依据；即使当前CommitId不变，候选变化也使旧依据StaleContext。
2. 同一短排他边界内，核对集合仍完整并固定必要文件保留，发布本次启动授权记录。新提交或根变动不能插入“最终核对”和授权之间。若需重新下载，退出边界重新准备，不持锁联网。下一进程无条件重读，旧授权不跨重启免检。
3. 将本次启动推进至加载阶段，再由M12准备匹配AOT并按依赖加载确定DLL。任一加载调用可能已改变进程状态后，失败只允许退出该业务入口并提示重启；不能在原进程装载R1替换部分R2，也不再次装载同名多版DLL。
4. 完整代码入口握手后固定本进程运行句柄，M10以该能力ResolveExact所需绑定，M02用M12 Load取得最新完整头并组织全部业务校验。若头／根与授权所据改变，回到核对；已加载集合无法覆盖时阻断并重启选兼容集合，绝不继续旧快照。
5. 各业务负责者校验通过后M02发布恢复视图、准确CommitId和可操作范围，M14记录BusinessReady。活动尝试的原EntryBaseline、历史、冻结及原版本保持；业务待办仍按原身份续办，不因“第一次新版启动”重发收益。

正常运行期间允许Prepare下一集合；已提交成长或晚到奖励可能新增旧绑定引用，Prepared不获得忽略这些变化的权利。请求重启时M02先形成可恢复边界并完成正在办理的H10，关闭表现不等于业务已保存。进程被系统终止则按已有完整提交恢复，不伪称未完成意图成功。

首个新版业务写入仍只能走H10，要求段与新正文同次提交。M14不设置另一个“首次写入完成”玩家标记来决定能否回退；每次回退都读取最新RecoveryRequirements，所以崩溃丢失更新诊断不会漏掉新档兼容要求。

## 6. 回退、保留与清理

代码回退也是一次目标集合的准备和下次启动启用。R2已经写出G11，R1只支持G10的格式／规则时，拒绝R1；保留G11、原绑定和包，等待兼容代码或另行批准的迁移。旧备份可读不能成为降级依据，M14不提供“恢复备份并继续”按钮。

保留集合取当前运行句柄、下次启动意图、正在准备／加载记录及M12完整引用根的并集；有业务引用的旧能力不能因远端不再列为最新被删除。集合文件共享时按实际内容身份去重保留，不凭目录年龄清理。

继承SD01首版**不自动裁剪已发布包**。清理授权逻辑只为后续明确批准的清理任务提供边界：先证明待删文件不在任何保留根，最终重核对与删除资格固定处于同一短排他边界；执行前还核对运行文件保留。授权不能留成可晚用的裸文件路径列表。根变化使未执行部分作废，重核对后续办；未知候选永不按超时作垃圾。

该规则没有授权本轮创建清理器或删除任何文件。部分下载残片、取消记录和失效验证缓存的处置也须证明没有执行／保留引用；磁盘满时先报告所需空间，不自动清玩家档、备份或旧规则。具体空间阈值不在本包捏造。

## 7. 中断与失败恢复表

以下为手工文档推演，**全部NOT RUN游戏／文件故障测试**；G10为当前完整头，R1为原可用集合，R2为目标集合。完成依据见第1节，保存判定沿SD02，不重新定义物理提交点。

| 输入／断点 | 输出与完成依据 | 重复／下一次恢复 |
| --- | --- | --- |
| X01：R1与当前所需资源完整，更新查询断网 | 原集合仍可核对并进入既定离线业务；没有R2启用结果。 | 不依赖查询成功重下R1；平台离线冷启动能力须另实测，未下载章节明确不可用。 |
| X02：首次R2只下载一半，无旧业务包 | 停在固定下载／错误界面；不进入游戏DLL，不初始化玩家档。 | 续同ReleaseSet并重新校验，齐备才Prepared；不会拼R1资源。 |
| 文件全到，但发布授权无效／AOT基座错／缺旧Rule | Rejected或UnsupportedBinding，保留原资料与R1。 | 更换内容不是原意图重试；修复后的明确目标另核对，哈希成功不能越过拒绝。 |
| Prepared(G10)后产生G11，或仅新增未决候选根 | 最终核对StaleContext，没有新启用授权。 | 读新摘要并重做能力／依赖差异核对；下载复用不等于复用旧授权。 |
| 启用记录发布前中断 | 没有确定新授权，保持可验证的旧阶段。 | 查询原操作和完整记录；新启动重读G10／更新头，重新核对目标。 |
| 启用记录可见但持久结果未知 | CommitUnknown仅指该更新记录的结果，不宣称已启用或玩家写档成功。 | 查询原阶段、补齐平台耐久检查；未知不启动另一套加载。 |
| 启用已授权，尚未调用AOT／代码加载 | 仍未CodeEntered；原玩家头不变。 | 下次启动重查全部依据；若当前进程改选原集合也须重新核对，无业务档回退。 |
| AOT已接入或DLL部分加载后异常 | 该进程不可继续切集合；固定错误界面给准确加载阶段。 | 新进程才重新选择R2或兼容R1；失败记录不是删除R2引用的依据。 |
| 入口成功，但M10解析失败或M02发现冻结／来源不一致 | CodeEntered成立，BusinessReady不成立，禁止业务写入并保留完整资料。 | 诊断归对应负责者；不靠改绑定、清历史、释放物品或赠补偿修复。 |
| 已BusinessReady，首个G11保存明确未提交 | 业务仍按SD02保持G10，不展示候选收益；R2仍是本进程集合。 | 重试原业务操作；若请求R1，下一启动仍查实际最新摘要。 |
