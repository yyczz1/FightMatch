## 1. 新增职责与保存对象

| Module | 独有职责与状态 | 向其他Module交付什么 |
| --- | --- | --- |
| M14 更新与版本切换 | 本机发布集合、下载／校验／启用进度、当前运行集合与启动失败记录。固定启动部分在热更新游戏代码不可用时仍能运行 | 向业务入口交付可用版本及兼容依据；M10解释配置，M12实施下载／文件与加载接入 |
| M15 游客与账号关联 | 本机资料到服务端主体的关联及绑定操作进度；服务端对身份关联结果负责，客户端只安装已确认结果 | 认证后的AccountId、原PlayerId的来源关联、待选档或待导入状态；不改角色／库存 |
| M16 云同步与选档 | 本机分支、局外检查点、待上传／安装进度、选档提案；服务端对云端当前版本和已完成同步操作负责 | 可核对的两侧状态与选择结果，由M02组织原业务负责者应用；不自行发奖或计算成长 |

这三个Module是新增职责，不要求新建三个QFramework System，也不要求分别部署服务。首版仍建议一个账号／同步后端应用。M14的启动部分仅保留必要代码；业务流程、主要UI和资源优先在热更新层。

玩家业务状态继续按S01～S18分别归属。来源凭据也跟随对应负责者：M08拥有Fact／Grant／Use关系，M07拥有固定发放及结算依据，M04拥有库存与消耗来源，M03拥有成长结果。M16负责组织核对，不能成为第二个背包或成长系统。

## 2. 最少共同身份与结果

| 语义名称 | 必须表达的区别 |
| --- | --- |
| `ReleaseSetId` | 一次不可变代码／资源发布集合，含适用平台和基座要求，关联原ContentBinding；不以单个资源版本代替规则身份 |
| `AccountId` | 服务端游戏账号身份；PlayerId沿用主契约的资料来源身份，绑定不重建业务ID。未正式绑定的广告校验主体与纯本机游客资料分开 |
| `BranchId / CheckpointId` | 分支及其不可变局外状态，保留共同祖先和来源提交；不靠本机时间决定覆盖，不包含可跨端续局的战斗历史 |
| `CloudRevision / CloudCommitId` | 服务端条件提交依据及已完成操作身份，区别于本机SaveGeneration／CommitId；云端成功不等于本机已安装 |
| `RewardResultId` | M08／M07关联原Fact、Grant、Use、原报价或Bonus的不可变固定结果身份；远端一份持久决定同时记录准确使用裁定及可恢复向量。不是本机CommitId，也不是可重复加到任意分支的奖励指令 |
| `SelectionProposal` | M16组织的固定候选：账号、两侧CheckpointId及祖先、所选普通分支、本机预期CommitId、CloudRevision、权益证据视图修订、逐项核对结论、各负责者候选及摘要。玩家确认只适用于这份差异；有未决必列出，不能包装为可完整安装 |
| `SourceSlice` | M04为受保护物品保存的逻辑份额：原Grant／发放行、稳定份额位置及数量；同一份额在分支复制后身份不变，拆分／合并堆叠不重编号。必须可判重叠和不相交，不能拿整个多张Grant当一张卡。具体编码与分摊算法留SD04／SD15 |
| `EffectReceipt` | 效果负责者产生的不可变结果凭据：效果身份、原发放／用途、准确输入份额、固定增量／产出与受益身份、绑定、原操作／提交，以及后继消费或准确撤回关系。证明发生了什么，不自行证明另一检查点已含结果；不能缩成全局used |
| `InclusionEvidence` | 各负责者在合法局外边界从本机来源收讫／后继索引产出的包含依据，绑定准确CheckpointId、BranchId、源CommitId及证据视图修订；指到同一份额当前的持有／转化／消耗或已批准待入账终点。M16据此比较，不按余额、等级差或收据ID并集猜缺失。活动战斗中的本机到账仍核对当前CommitId索引，不伪造新检查点 |
| `BeneficiaryMapping` | M15提供资料来源到AccountId的已验证关联，M03给原PlayerId／CharacterId到目标角色的一一对应、依据及规则兼容结果。相同源身份或有证据的既有关联可用；同名／同职业不足，缺失角色不是自动创建授权 |
| `RecoveryRequirements` | M12交付的版本化只读摘要：PlayerId、当前CommitId／SaveGeneration、当前／有效备份／未决候选引用根依据、封套与业务切片版本、完整内容绑定和执行能力要求、摘要完整性及未知项。无需热更业务类型即可读取，不含另一套成长／战斗算法 |
| `ReleaseCapabilities` | M14固定ReleaseSet的基座／平台、代码／必要AOT／资源身份、可信发布及完整性依据、可读保存版本、可执行Rule／Numeric／Random版本和可提供内容绑定。M10核对定义；“支持某版本”仍须详细任务给验证证据 |

本稿操作继续使用稳定OperationId和原输入指纹。已完成的同一操作先返回原结果，再考虑当前版本是否变化；不同意图不得借同ID重试。`PendingExternal`、`CommitUnknown`、`StaleContext`、`UnsupportedBinding`沿用原含义。下文`ReconciliationRequired`表示有具体核对缺口，保留资料并返回原因，不是假装成功后的静默少发。

跨网络流程分别报告远端结果和本机安装结果。只有本机完整状态已按H10提交，才能向游戏业务报告原`Completed`；不能新增一个同名状态来降低其保证。

远端阶段统一返回原OperationId／意图、对象、`Confirmed / Rejected / Unknown`及可查询依据；Confirmed携确切关联结果、CloudCommitId、Use许可或RewardResultId，绝不省掉完成对象。下文ResultCommitted是Confirmed所确认的固定结果阶段，含RewardResultId及固定结果，不是另一套未知／成功分类。Rejected须确定该远端意图未成；超时为Unknown，沿原操作查询。H12/H13的本机安装是关联父操作的另一个稳定子操作，不能把同一OperationId从“申请远端”改成“本机写档”。终止传输不终止远端事实，旧回执只补记原阶段，不重新执行用户意图。

## 3. H11 小启动层、内容取得与版本启用

**发起／接收：** 启动或明确的更新重启意图交M14；M12给RecoveryRequirements及平台能力，M10给定义解析结果，热更入口交M02恢复业务。准备、启用分别绑定OperationId、ReleaseSetId和摘要依据；下载重试仍取同一集合，不悄悄改成远端最新。

| 操作 | 输入与输出 | 完成／失败约束 |
| --- | --- | --- |
| 准备可用版本 | 当前基座／平台、已提交存档所需绑定摘要、目标发布集合及当前所需内容；返回本机可用、待下载或不兼容 | 已有完整可用版本时，更新查询失败不阻断普通离线游玩；未下载内容明确不可用 |
| 取得缺失内容 | 固定ReleaseSetId和需要的依赖集合；输出进度及经过校验的文件 | 只准备候选，不把部分新代码、旧配置与新资源拼为可运行版本。所需依赖完整不等于下载所有章节 |
| 进入游戏版本 | 完整代码集合、必要AOT依据、匹配内容和存档绑定摘要 | 按依赖加载代码后才实例化带热更脚本的场景／Prefab；业务恢复完成才报告可游玩 |
| 请求切换版本 | 已准备集合及当前运行／业务状态 | 运行中准备，明确重启后启用；本轮不依赖同进程卸载／替换程序集 |

固定启动层负责最小进度、错误与重试显示，不能依赖远端游戏DLL才能恢复下载。M12以与本机提交关联的只读摘要提供恢复所需版本身份；M14只检查版本能力，不解释角色等级、背包和战斗规则。摘要缺失／不一致不是新玩家，不能清档或擅自改绑定。

进入热更新入口后，M02调用M12读取完整存档，由M03～M10等负责者核对各自状态。启动成功包含“代码可运行”和“本次业务资料恢复完成”两步。任一步失败保留原资料与受引用版本，不靠回滚玩家业务来使旧代码可读。

发布集合一旦被新业务提交引用，其清理和回退必须重新核对最新存档、备份和未决提交的引用。仅保留旧配置JSON不能证明旧规则仍可执行。M14管版本，M10管定义，M12管物理取得／保存，避免三个Module各自选择不同的“最新版”。

**O05共同收口：** 摘要必须与所指完整提交一致；缺失、不一致、无法完整枚举引用根或未知摘要版本均返回RecoveryBlocked，不初始化新玩家。M14以ReleaseCapabilities覆盖全部RecoveryRequirements；当前可执行头与备份保留根分别标明，不能把备份当可写头。启用／回退／清理前重新核对CommitId及根依据，已变则重新准备检查。代码加载后M02仍做完整业务校验，摘要通过不代替它。摘要编码、物理提交及清理实现交SD02；稳定入口、发布信任及平台组合交SD13。

M10的当前绑定只在M14已启用集合中选择；下载新集合不改变当前进程的规则范围。同一已启用集合内按需取得其声明的关卡依赖不等于换规则。候选可信发布依据与文件完整性均通过才可执行；普通内容哈希不独自证明发布授权。首版保留旧规则能力，不依赖同进程装载同名DLL多版；不兼容时保留原资料和可用集合，禁止以旧玩家档配合代码回退。SD01／SD02原设计按此新增交接各作窄修正。

## 4. H12 游客绑定与资料接入

| 阶段 | 负责者与可观察结果 | 不可提前宣布的结果 |
| --- | --- | --- |
| 本机游客游玩 | M02创建／恢复原PlayerId；M12本机保存 | 不依赖在线匿名登录或正式注册完成 |
| 认证目标账号 | M15经M12取得可验证主体和AccountId | SDK登录成功不等于原进度已接入 |
| 申请关联 | 保存稳定操作与原资料来源；服务端验证目标身份及原游客广告主体的控制权 | 不用本机声称的PlayerId领取他人的云档／权益，不自动强制迁移已属别人的认证关联 |
| 选择／导入进度 | 无云档时接入可同步局外检查点；已有云档时转H13明确选档 | 不以绑定为理由重发首证、首通、广告奖励或终止本机战斗 |
| 本机安装关联结果 | M02组织H10提交，保留原身份到账号的来源关系及待办 | 完整提交前不删除游客原资料，不把云端成功当本机已完成 |

绑定与进度导入可有不同完成点。网络回执丢失时查询同一操作；账号已关联但进度未导入时显示该实际阶段，不重新创建账号或重复导入。绑定期间原游客广告的晚到回执仍定位原请求，再按已确认关联接入。

原设备仍有活动尝试时，关联身份和上传必要广告事实可以办理，普通进度仅使用上一个可同步检查点。本机继续保留原尝试；选择远端状态不直接覆盖它。账号、角色、关卡及结算的来源映射分别保留，角色显示名或相同LevelId不能充当身份合并依据。

**O04身份交接：** M15只能证明资料归属，M03再返回`Mapped / MissingBeneficiary / AmbiguousIdentity / IncompatibleRules`，携准确对象及证据。共同祖先中同一角色的分支副本可按原CharacterId核对；两个独立游客各自创建的战士不能只凭同职业合并。已确认关联与角色可应用性是两个检查，不相互冒充。

**已确认的缺法师案例：** A过8获得法师并使用独有广告经验卡，玩家选未过8的B；用户明确选择“保留这笔固定经验，B正常解锁法师后入账”。M03给出待正常解锁的固定效果候选，保存原EffectReceipt／SourceSlice、固定经验量、原受益来源及法师解锁条件／绑定，随H13选档候选同次H10持久化；M16只组织核对。不得提前创建法师、给其他角色、退回原卡、重按新卡倍率算经验或导入A普通进度。

待入账是M03持有的业务状态，不是经验已经到账。H13可对这份已获产品许可的候选完成安装，结果明确列“固定经验已保留，待法师解锁”；InclusionEvidence把该来源指向待入账终点，重复选档或同步不能再次建份额。缺角色时保留原受益来源和解锁要求，不伪造已经映射的目标CharacterId。安装时目标已解锁或CommitId已变，按H13重新核对并只产生待入账或直接应用中的一种结果。

M05提供B正常解锁依据，M03核对资料来源、合法角色对应和计算兼容后，将固定增量、角色创建／成长、目标映射和待入账→已应用凭据同次H06/H10提交；失败仍全旧态，未知查原提交。角色先按B正常解锁配置初始化，再加固定广告经验；不复制A等级／技能／恢复，也不追补B第8关战斗经验。该增量不进入B的BaseReward，不能参与其后结算广告倍率。去重依据为原固定效果与SourceSlice，不仅是本次OperationId；同来源不同数额／受益身份返回冲突，换操作ID、重复解锁或到账均不再增加。

已应用后保留来源收讫／后继凭据，再选无角色档必须沿该证据核对，不能重放原经验。身份或规则不兼容时保留待入账并报告原因，不因这笔待办阻止B正常解锁；兼容恢复后另以稳定操作联合应用，不能先清待办再加经验。该决定不批准独立游客角色合并或所有缺失对象一律延期。SD03／SD05／SD14／SD15须细化上述交接与断点。

## 5. H13 局外检查点、选档与本机安装

**发布检查点的工作方案：无活动尝试，且基础结算已完成。** 本机战斗、冻结和撤销历史仍完整保存；云端提供上一份合法局外状态。广告事实及必要使用凭据可以另外传输，但必须说明哪些效果尚未包含在普通检查点中。

用户补充“战斗如果不能同步，那就放弃同步”，由架构交接r2接收：新设备从已同步局外状态继续，原设备仍可读本机档则继续原战斗；设备与本机档一并丢失时不恢复该战斗。O03不能靠增加战斗同步解决；丢失战斗不证明未知广告Use已生效或未生效，也不授权超时重发。

| 步骤 | 共同Interface及完成条件 |
| --- | --- |
| 产生检查点 | M02收集各负责者已提交状态，M16登记原CommitId、分支祖先、版本及权益包含依据；无未完成基础结算或未解释冻结 |
| 读取云端并比较 | 返回云端当前版本及相应权益核对依据；同一条分支可推进，有真实分歧则形成SelectionProposal |
| 核对候选 | M03／M04／M05／M07／M08分别判断导入结果；先解决已知缺口，再向玩家展示可确认差异；不由UI或M16自行加经验 |
| 确认选择 | 绑定原提案、两个检查点、期望云端修订及权益依据；任一相关依据变化则重新核对并展示，不把旧确认用于新差异 |
| 服务端条件提交 | 服务端记录同一操作的新云端头和CloudCommitId；竞争失败返回当前事实，回执未知时先查询原操作 |
| 安装到本机 | M02在稳定业务边界使用各负责者候选，连同云端结果和来源记录按H10完整提交；成功后才显示切换完成 |

构造／上传提案可以异步进行，不长时间占用本机业务写入。最终确认与安装必须检查本机预期CommitId；提交未知期间暂停的是与该切换冲突的写入。不能让旧远端回执覆盖期间产生的新本机成长。若本机状态已变化，保留远端已完成结果与本机分支，进入重新核对，不将远端事实回写成失败。

云端已提交而本机安装中断，续办该CloudCommitId对应结果；本机业务已完成但上传失败，则保留待上传状态，不回滚离线成果。恢复先处理原未决操作，再决定是否需要新提案。服务不可达时普通离线游戏保持；不能把“核对未完成”宣称为跨档收益已无损保护。

**证据与安装的共同不变量：** 检查点、普通业务状态及InclusionEvidence必须来自同一提交；新到的Fact／Use属于另一修订，不能悄悄拼入已确认提案。服务端条件提交同时核对云端头与权益证据视图；缺少此能力不得宣称X06通过。确认时若本机已有活动尝试或CommitId已变，旧提案不能安装；保留原本机分支，按新事实重新展示。安装联合包含成长／库存／进度等候选、来源收讫／后继依据及原远端结果，缺一不报Completed。来源凭据不足只能返回ReconciliationRequired，不能用空集合冒充“从未包含”。

固定奖励的RewardResultId随同来源核对：ResultCommitted但本机未安装者只表示有一份可恢复的固定应得结果，不表示当前检查点已含。目标已含或已有后继消费不再按原向量追加；账号级“已安装”标志不能代替目标分支证据。远端原发放不能证明设备丢失前尚未上传的用卡／合成终点，此类缺证仍受O01／O02约束；第10节仅对已获用户许可的永久丢失经验卡作明确政策处置，不冒充找回后继。

## 6. H14 一次广告机会的联网使用与精确撤回

本节扩展H07／H05，不改变用途和合法目标。**本地目标效果许可路径**继续用于局内复活、局外恢复、直接通关等尚未证明可走固定结果的用途；阶段见下表。资源广告和目标可合法对应的结算增量采用后述**固定结果路径**，不能把两套NoEffect条件混用。请求持久记录采用的协议语义版本，旧未决操作不得因更新就推断未生效。M08对接账号／同步服务，M06／M03／M07等负责者决定实际效果，M02组织本机提交。 在线攻略的挑战服务与单次请求不同，其许可／交付／关闭的专门约束见第13节，不因一次分析失败就释放整份服务。

本表表达必须满足的交接，不指定数据库事务或超时租约。服务端许可成功不是本机效果成功；本机EffectCommitted与服务端确认不同步时，原意图仍须可查询。正常再次死亡或退出不自动撤回有效使用。旧Use的迟到撤回不能释放后来的新Use。

**永久丢失的已定例外：** 用户已选择“恢复这次机会，接受可能已用过一次（推荐）”。只在原设备和本机档永久不可恢复、准确局内复活Use的效果仍无法核实时，允许恢复原Grant的一次可用机会；不修改历史为“确定未生效”，不恢复旧战斗，不扩展到普通断网／超时、局外恢复、通关、资源卡或结算。详见计划第27节。 第14节是另经用户批准的在线服务恢复，不能从本局内复活例自动类推。

**效果事实与资格处置分开：** M08结合M12及远端证据仍给`EffectCommitted(receipt)`、`NoEffectFinal(proof)`或`Unresolved(reason)`。前者只说明准确效果已提交，跨档应用另走H13；中者证明无效果且旧许可不可再执行，可按原协议释放；Unresolved禁止直接新用，但满足上述例外时可申请独立恢复裁定。一次本机ConfirmedNotCommitted、未收到确认或超时都不等于NoEffectFinal。

**恢复裁定RecoveryDecision：** 原主体、GrantId、被替代UseId、玩家明确的永久丢失声明、原用途／受益身份、预期资格修订和稳定OperationId须固定。服务端核验身份与该准确Use仍待确认；声明是本规则输入，不假装能由离线时长证明或能删除丢失设备的旧缓存。以原Grant／Use的恢复业务键防重，同一可查询持久决定同时记旧Use授权已被替代、恢复资格及新修订。保留原Fact／Grant，不新造观看或多发余额；这不是本机复活已完成。

同一Use重复／改OperationId申请返回原裁定，不能在后续新Use已使用时再次释放；新使用仍联网取得不同UseId并校验合法角色及当前场景，不能复用旧许可。恢复后再次发生同类永久丢失时，对准确后续Use重新应用同一判据，不能借递归恢复让同一Use重复返还。

恢复与EffectCommitted／NoEffectFinal／撤回／新使用按同一资格修订串行裁定：确定效果先成立则不适用本例外；原协议已释放则返回现状，不再追加；恢复先成立则晚到旧效果／撤回只记旧Use历史，不能收回恢复出的机会、修改当前新Use或再返一次。远端结果未知先查原裁定，本机安装未知先H10查询；本机缓存不能授权新用，恢复成功后显示当前服务端资格状态，不拿旧“可用”快照覆盖后续已用状态。实际归属、准入、持久化与迟到隔离由SD07／SD15及SD06给出限定证明；完整O03不因产品决定即结案。

**固定结果路径（原架构已定向接收的受限方向）：** 只用于原报价确定的资源发放，以及受益身份和规则可合法对应的固定结算广告增量。局外恢复、整场广告通关、混合合成和局内复活不自动纳入。原架构任务`01a0a020-2283-7580-abf1-fc3c9e4ef08e`已实际回复，授权方向及证据限度见本轮审阅记录；这不是云端实施验收。

| 阶段 | 必须满足的交接与可观察结果 |
| --- | --- |

## 7. 广告来源及跨档核对

用户已确认：目标档完全不含另一侧的独有广告奖励时，保留其直接奖励及已转化结果；同一张已领广告卡在两端发生分歧消费时，只保留所选档的一种结果。本轮补充了持有／消费分歧：A已用卡、所选B仍持同一卡时，保留B的卡，不导入A由此取得的经验；不把被舍弃经验转成待解锁项。其他独有来源继续保护，决定和界限见[计划第23节](session-plan.md#23-用户补充决定同一卡已用与未用跟随所选档)。后续普通闯关成果仍随普通选档，不因受广告帮助而自动受保护。

最低证据包括：原固定发放及用途、可区分的来源份额、消费对应的来源分摊、实际转化结果及受益对象、结果所在分支／提交、目标分支的已包含或已消耗证明。来源耗尽仍须留足防重证据；库存为0不等于该档从未收到。分配粒度是详细设计项，不要求所有普通物品逐件编号或全量事件溯源，也不能把一张卡的决定扩大为整批Grant必须共同选档。

**O01共同份额约束：** 首版整数物品必须至少区分原发放行内的逻辑单位；可用稳定序号区间表达，物理上无需为每张卡建立对象。M04在消费提交前固定实际分摊，跨分支沿用原份额身份；M03／M07把固定效果关联到这些输入。每份额在一个分支只处于一个有效终点，后继转换引用前序，不能同时计原物和产出。简单定额卡可按明确单位拆分固定经验；混合／不可分产出没有经审定分摊规则就不能按比例拆。普通物品只在证明混合投入时补足必要依据，不要求全游戏事件溯源。

**同种经验卡消费顺序已定：** 用户回答“先扣广告”。同ItemId、同单位经验的可用卡先分配广告来源，不足部分再分配普通来源；类别内沿M04稳定顺序。预览固定成本份额，确认核对修订；重试沿原分摊，不追溯改已完成消费。M03固定经验行必须对应这些实际份额。此决定不新增卡种或投放，不改变数量／价值，也不外推材料、战术消耗或不可分合成，原答及出处见[计划第24节](session-plan.md#24-用户决定普通与广告同种经验卡先扣广告)。

InclusionEvidence逐份额至少判为`Absent / SameEffect / DescendantConsumed / SelectedConsumption / SelectedHolding / Unresolved`：Absent需要完整原发放范围及目标包含索引证明；目标自己的后继消费链归DescendantConsumed；同一卡分歧中所选终点为已消费时归SelectedConsumption，所选仍持卡且另一侧已消费时归SelectedHolding。后者保留该份额原卡，另一侧消费凭据仅作核对历史，不成为可重试的新欠账；以后所选档正常用这张卡只生成一次新的有效终点。第4节已批准的待解锁经验也有唯一有效终点；同一待入账结果再次出现归SameEffect，不等于角色经验已增加。缺证、混合不可分及未获批准的角色不兼容仍列Unresolved并附原因；没有准确份额身份不能套持有／消费决定。所选状态中同一份额已持有时，也不能把另一端经验视为Absent再追加。

**共同见证（符号数量，不是配表）：** G发三张、每张固定e经验，份额g1/g2/g3。A把g1/g2转给同源战士，B完整证明从未含G，则候选仅加2e与g3；重试不加，B后来消费g3后遇旧A也不补卡。部分包含必须交完整产生链：另例A只先消费g1，B完整接入g1效果及g2/g3卡；随后A把g2给战士，B把g2给法师并沿原接入链消费g3，A又取得独有J。选择B时g1同效、g2只留B消费、g3已有后继，仅补确证未含的J。不能把“B没见过A的g2效果”当g2来源Absent；B仍持g2则按本轮决定保留g2卡、不导A的对应经验，B已消费则按准确分歧核对。r2省略g2来源状态的“只补g2”例由此替换，不作为合法稀疏存档的证明。详细份额表见SD15-R1及R2补充，均为设计推演，不是测试通过。

| 对比结果 | 设计处理 |
| --- | --- |
| 目标档从未包含独有来源，且直接结果可合法接入 | 各负责者按原依据接入该来源剩余物品和已转化结果；不重发原奖励或覆盖整个角色 |

此方案能为已确认的经验卡例定义一致目标，但未证明任意混合资源与合成结果都能自动合并。[正式主稿](../../game-design/2026-09-14-fightmatch-game-design.md)已包含广告发普通材料及首版固定配方制作职业消耗品；混合来源不是仅有未来永久装备才会发生的问题。[三组稿](../../game-design/2026-09-15-three-group-recommendations.md)的飞斧具体配方仍是候选，不据此声称已完成数值可达性验证。SD04／SD07／SD15须先列出首版实际转换，再把无法兼容所选普通投入的案例交策划／用户裁决，不能用技术去重替代这一取舍。

广告复活后的普通胜利、广告直接通关及结算广告增益须按各自用途区分：不能把复活后的全部普通收益认作直接广告奖励，也不能只保留直接通关的used标记而丢掉其已交付结果。各用途的具体保护范围与混合来源规则见独立审查，缺口进入相关系统设计。

### 承诺与取消的竞争

M08对接的原账号／同步后端须对同一Grant当前Use及资格修订作一项串行、可查询的条件决定；不是先写used再另存结果。读取旧状态后分别写入承诺和取消、或先返回成功再异步补向量，都不满足该约定。未决记录在故障恢复时必须有唯一可确定的终点，不能由最后到达的回执覆盖。

- 承诺先完成：保存Use→RewardResult及完整向量；后到取消返回该已成结果，继续安装，不释放Grant。
- 终止先完成：保存该Use的NoEffectFinal及不可再承诺关系；后到旧提交拒绝或返回原终止，不使旧Use复活。原Fact与已完成广告的期间占用不被取消Use抹掉，也不占新期间一次额度。
- 两项都未知：分别查询原操作并核同一资格当前修订；确认前不取另一Use、不重报价。传输取消不等于业务取消。
- 后来合法Use已变化：旧终止／旧承诺查询仍返回其历史结果，同时当前资格按最新修订显示；不能拿旧“可用”投影覆盖新Use，或让旧终止再次返还机会。

只要本Use明确采用固定结果协议，未承诺且已被权威持久终止就使首次本机安装无合法前提，因而可以成立该路径的NoEffectFinal。此论证不能迁移到先取许可再做本机效果的旧协议；那些操作仍可能已本机生效，须沿原H14效果证据处理。
