## 1. 依据和范围

承接[架构基线r1](../../architecture/2026-09-16/review.md)、[C4视图](../../architecture/2026-09-16/c4/README.md)、[层级说明](../../architecture/2026-09-16-architecture-scope-and-system-collaboration.md)及[2026-09-17设计交接](../../handoffs/2026-09-17-system-design.md)。玩法使用[最新接收与G01](../../architecture/2026-09-15-content-requirements-sync-reply.md)、[主策划](../../game-design/2026-09-14-fightmatch-game-design.md)、[三组规则](../../game-design/2026-09-15-three-group-recommendations.md)与[同步F／G](../../game-design/2026-09-15-content-planning-sync-reply.md)。较新的明确决定覆盖历史候选。

本稿的 Module 是封装业务能力的模块；Interface 包括输入、输出、顺序、拒绝和完成条件，不等同于 C# `interface`。Seam 是调用方通过该 Interface 使用能力的位置；只有确实需要替换的接入才设计 Adapter。职责数量不直接决定类、QFramework System 或程序集数量。

现有代码核对范围：`Assets/Scripts/FlowPuzzle/` 已有 Core、Generation、Validation、Solving、Application、Persistence、Editor 等代码及测试，不能沿用 6 月的空仓清单。已读的 `FlowCompletionRequest`、`FlowSolveRequest` 只接收几何、固定路径及搜索预算；`FlowSolutionValidator` 验证完整配对路径，并非 RPG 行动或胜负验证器。现有 `FlowSolveStatus` 已区分 NoSolution、Timeout、Cancelled、InvalidInput、Error；RPG 验证必须保留这种区分，不能把几何结果升级为战斗结论。本轮未修改或执行这些代码。当前 `Packages/manifest.json` 未列 QFramework，不据此认定任何具体版本已安装。

## 2. 共同方案与成本

以下为本轮明确推荐，均属**设计建议待审阅**。后续详细设计以这些语义为共同输入；若否决，先由统一设计负责人修改共同契约，不允许各系统各选一套。

| 选择 | 推荐方案及理由 | 成本与限制 |
| --- | --- | --- |
| D01 跨系统一致完成 | 单机一个业务写入队列；各负责者验证并产生自己的候选变化；保存完整一致版本成功后一次发布。应用流程或结算协调组织，不使用相互监听事件拼接扣资源与发奖励。 | 要构造候选数据和稳定操作记录；磁盘失败时暂缓后续变更。无需数据库、分布式事务或新依赖。物理原子保存由平台详细设计验证。 |
| D02 库存与当局携带 | 长期总拥有量包含已装配与已冻结量；入场按 attempt 冻结携带量，当局仅减少本局余量。胜利扣实际用量并释放冻结；放弃仅释放冻结，不额外增加总拥有量。 | 查询需区分总拥有、可用、装配和本局剩余；需要验算数量守恒。避免每发攻击跨写长期库存。 |
| D03 战斗历史 | 普通 C# 战斗 Module 内保存规则操作前的完整状态及操作／结果记录，跨面不断历史；战斗回退只恢复战斗切片，权益使用通过显式交接恢复。 | 长局内存与保存体积增长，需要后续测量；不能据此暗设回合上限。场景修订号与操作防重记录不随回退倒退。 |
| D04 一份规则，多份独立局面 | 客户端、内容验证、攻略验证使用同一普通 C# 规则 Interface：入场建立局面、对独立状态求一次完整转移、输出结果和新状态。QFramework 负责客户端组织。 | 输入需包含所有规则依据、开关、随机状态及剩余 Boss 面；验证不得偷读玩家 Model。在线搜索部署与供应商可后置。 |
| D05 配置发布与绑定 | 内容维护产出一个不可变发布包；客户端、默认攻略和验证绑定同一配置身份、规则版本、数值和随机契约。编辑源格式可在内容详细设计选择。 | 需维护引用校验和旧版本可恢复性；运行中不能热换数值。成长回放 CSV 不是运行时定义或存档。 |

单机主线程顺序处理业务判断，网络／广告回调进入同一队列；重搜索在独立数据上执行，不持有业务写入锁。业务事实提交后可通知 UI；通知丢失不影响事实，重开页面从当前已提交状态重建。

## 3. 16 项职责及对外能力

编号 M01～M16 为本稿索引，不是要求新建 16 个 System。对外返回的状态均为只读资料；玩家业务修改只能通过所属 Module 的请求及 D01 提交。启动版本、认证和远端操作分别遵守H11～H14的完成点，不能用单机提交替代网络协议。

| 编号／Module | Interface：接受什么，给出什么 | 独有状态／修改权 | 依赖及明确不负责 |
| --- | --- | --- | --- |
| M01 输入与表现 | 提交选人、连线、补线、回退确认、页面意图；读取已提交视图和结果序列；回报指定演出令牌完成。 | 选中对象、拖线草稿、窗口与动画进度。 | 只向 M02 提交业务意图；不写 HP、库存或胜负；不因动画回调推进回合。 |
| M02 应用流程 | 入场、教学、永久操作、行动、回退、广告兑现、退出与加载的组织入口；返回可操作范围和稳定操作结果。 | 页面路由、流程办理阶段、演出门闩及已确认操作身份。 | 调用相应负责者；D01 是其组织机制，不把所有业务规则搬入此处。结束奖励计算交 M07。 |
| M03 角色成长与职业 | 查询角色／阵容／恢复；预览培养与学习；提出经验、职业获得、学习、阵容及恢复候选变化；生成入场基础资料。 | 长期等级经验、已获职业技能、阵容、局外恢复。 | 读 M10；消耗通过 M02 组织 M04；不自己扣证／卡，不接管教学，不追改正在进行的战斗基础属性。 |
| M04 背包与战术装配 | 查询数量及装配；预览配方；提出消耗／发放、合成、装配、冻结／结束交接及开关偏好候选变化。 | 总库存、材料、局外分配、attempt 冻结记录、每角色当前开关。 | 读 M10；入场／结束凭战斗交接资料；不算伤害，不在救援等待返还，不改变等级。 |
| M05 关卡进度与教学 | 给出开放与开战条件、待办教学；判断一次赠证／首通；创建或续用 challenge；提出教学、通关和挑战关闭变化。 | 开放、首通、一次领取标记、教学步骤、未通关挑战关系。 | 读配置及交接的最新成长资料；赠证与学习交 M02 协调；不直接加库存，不持有第二份战斗状态。 |
| M06 战斗与回退 | 创建尝试；校验并计算攻击／补线／复活／回退／结束；输出完整局面、顺序结果、历史锚点、阶段及最终报告。 | 本局棋盘、敌我、物品余量、历史、随机／PRD、实际贡献、复活使用引用。 | 读固定入场资料、M10 及 M13；不读可变背包／UI，不保存广告事实，不发永久奖励。 |
| M07 结算协调 | 接收封闭的尝试报告；冻结原始奖励；组织正常胜利、广告通关、放弃返还和结算增益；查询办理结果。 | attempt 结束记录、基础结算记录、原始奖励、增益记录。 | 向 M03／M04／M05／M08 提交各自负责的变化；不自行改等级算法或重新模拟战斗。 |
| M08 广告权益 | 注册广告用途与对象；接收可核验完成事实；查询资格；提出一次兑现及对应使用撤回；报告未兑现原因。 | 广告事实、复活机会、在线挑战资格、广告用途绑定与兑现状态、资源广告限额。 | M12 报告事实，业务负责者裁定效果；自己不复活、发物品或写通关。 |
| M09 攻略 | 提供免费默认参考；取得当前分析快照；请求候选；用独立规则验证；返回内容、适用条件和分类结果。 | 默认／在线内容、请求状态、验证依据、已保存攻略及适用局面。 | 读 M08 资格、M05 挑战、M06 快照、M10／M13 规则，经 M12 联网；不自动执行玩家操作，不消费真实物品。 |
| M10 配置与内容 | 按发布身份提供一致只读定义、引用关系、规则兼容信息及参考资料。 | 已发布的职业／成长／技能／物品／配方／敌人／关卡／奖励定义。 | 受控接收 M11 的通过产物；不持有玩家经验、HP、库存或 CD；不从工作簿回放行推断玩家资料。 |
| M11 内容编辑与验证 | 编辑 RPG 草稿；运行结构、几何和完整战斗验证；返回诊断、见证与适用条件；申请发布。 | 草稿及验证结果。 | 组合 M10、M13、M06 独立验证局；不访问玩家写入入口，不替换通用 FlowPuzzle 编辑职责。 |
| M12 平台与保存 | 播放指定广告请求、报告原始回执；传输分析请求；保存／加载业务一致版本、查询操作提交结果；提供时间依据。 | 接入请求技术状态、保存代际与校验资料。 | 不解释奖励和学习条件，不以文件存在或 SDK 回调自行宣布业务成功；接入 Adapter 与业务资格分开。 |
| M13 通用棋盘能力 | 几何数据、路径合法性、生成、编辑、几何解及诊断。 | 独立几何输入／结果，不拥有 RPG 当前对局。 | 不依赖职业、库存或奖励；无满盘和唯一解要求。现有完整解验证 Interface 不应被假装成已具备单次 RPG 攻击校验。 |
| M14 更新与版本切换 | 准备可用发布集合、安排缺失内容取得与校验、选择启动版本、请求重启启用；交付可运行且兼容的版本依据。 | 本机发布集合、下载／启用阶段、当前运行集合及失败记录。 | M12实施文件、下载和加载接入，M10解释定义；不解释成长／战斗规则，不用旧业务档配合代码回退。 |
| M15 游客与账号关联 | 认证账号、关联原资料来源、查询绑定阶段；已有云档转交M16形成选档提案。 | 绑定操作、本机安装的身份关联；服务端是账号关联权威。 | 经M12接入认证；不自己合并角色、发奖或覆盖存档。SDK登录成功不等于进度接入完成。 |
| M16 云同步与选档 | 登记局外检查点、比较共同祖先、组织来源核对、提出选档候选、条件提交和查询同步结果。 | 本机分支、检查点索引、提案与同步待办；云端头由服务端裁定。 | 由M02组织原负责者形成并安装业务候选；不成为第二个背包、成长或结算系统，不上传活动战斗供跨端续局。 |

**QFramework 映射建议：** M01 为客户端交互与显示；M02／M07 为明确组织业务的流程；M03／M04／M05／M08／M09 按状态负责者管理客户端业务与只读视图；M06 的客户端入口承接 QFramework，规则与历史本体是普通 C# Module；M10 提供只读定义；M12 放接入 Adapter；M11 是 Editor 制作入口，M13 延续通用几何代码。这里只采用分层方向，不假设已核实 QFramework 安装、版本或任何具体方法。

M14的最小启动能力在业务代码不可用时仍须运行；M15／M16的业务流程和主要UI优先热更新。三个新增职责不要求拆成三个服务，首版建议一个账号／同步后端应用；具体程序集与供应商留给相应设计。
