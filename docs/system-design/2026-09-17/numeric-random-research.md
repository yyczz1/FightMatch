## 3. Unity／C# 的保证边界

| 主源直接结论 | 本项目能据此作出的判断 |
|---|---|
| Unity 2022.3 的 Random 是共享静态状态；其 State 可获取、设置和序列化，用于跨会话恢复确定序列。[Random](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Random.html)、[state](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Random-state.html)，核查 2026-09-17 | 可用于其文档范围内的状态恢复；文档未给出本项目要求的跨语言状态字节格式、种子映射和全部抽取次序规范。不能推成跨端逐位验收已通过。 |
| `Math.Log` 的微软文档说明底层使用 C 运行库，精确结果可能随操作系统或架构而异。[Math.Log](https://learn.microsoft.com/en-us/dotnet/api/system.math.log?view=net-9.0)，核查 2026-09-17 | 宿主 Log 不能单凭 API 名成为逐位规范；该文档也不证明 Unity 内某个样例已经出现差异。 |
| `System.Random` 不保证跨 .NET 主版本维持同一实现／同种子序列。[System.Random](https://learn.microsoft.com/en-us/dotnet/api/system.random?view=net-10.0)，核查 2026-09-17 | “保存 seed”不足以替代版本、完整状态与取数协议；这里没有假定工程运行 .NET 10。 |
| Unity 2022.3 支持 Mono 的 JIT 与 IL2CPP 的 AOT。[后端说明](https://docs.unity3d.com/2022.3/Documentation/Manual/scripting-backends.html)，核查 2026-09-17 | 编译路径是设备验证矩阵的输入；本次没有检查工程后端配置，不能声称两者当前均启用。 |

【主源保证】C# 整数除法向零截断；溢出在 checked／unchecked 上下文中处理不同。decimal 也不能精确表示所有除法，例如三分之一。[算术运算符](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/arithmetic-operators)，核查 2026-09-17。
【设计推论】战斗正数域可证明向零等于 floor，负数域必须另外规定；业务数值不可借 unchecked 回绕继续计算。decimal 不能独自解决评分 log₂。
【主源保证】uint／ulong 的右移补零，移位数分别取低 5／6 位；移位本身不受 checked 影响。[位运算](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/bitwise-and-shift-operators)，核查 2026-09-17。
【设计推论】PRNG 应显式使用无符号固定宽度及模回绕，与业务算术隔离；不依赖 Unity 未核实支持的新 C# 运算符语法。

## 4. 两种最小数值表示方向

| 候选 | 精确覆盖与代价 | 尚须补足 |
|---|---|---|
| A：约分有理数 n/d，d>0；评分使用有界区间 | 配表十进制文本、`8/5`、`5/4`、成长、护甲分母及奖励系数可按有理运算保存；只在指定业务出口 floor／ceil。log₂ 另作带证明的近似。 | 输入范围、约分时机、乘积宽度及超限策略；64 位不足时是否采用更宽整数表示须验证，不能假定已有库可用。 |
| B：固定尺度整数 v/Q，评分使用固定表或固定多项式 | 状态宽度和每步操作易写成规范；但不在该尺度上的值必须量化，近整数边界可能改变结果。 | Q、有效域、中间乘积宽度、每一步舍入、系数精确位型、误差界及改变既有结果的审计。 |

【设计推论】A 从原始数值文本生成整数分子分母，不能先经二进制 float 再声称恢复了十进制精确值。分母约分不改变值，但资源耗尽策略必须显式失败或转入已批准表示。
【设计推论】B 选十进制尺度仍不能消除任意分母：例如 `23.6×100/(100+1.5)=4720/203`；选二进制尺度则 `0.08` 本身也不能精确表示。两种情况下都要分析最终 floor，而不是只比较显示误差。
【设计推论】当前材料未给出足以证明所有贡献累计和乘积始终装入 long 的边界；不得为了采用 64 位表示而自行增加贡献上限或缩短完整回退历史。
【设计推论】下一小包优先论证 A 的奖励评分出口，B 保留为有明确范围／误差预算时的备选；这不是正式 Numeric 版本或整场战斗实现选择。

## 5. log₂ 的最少确定方向

【主源保证】对本任务正实数域，可用 `ln z = 2(t+t³/3+t⁵/5+…)`，其中 `t=(z−1)/(z+1)`。[NIST DLMF 4.6.4](https://dlmf.nist.gov/4.6#E4)，核查 2026-09-17。
【设计推论】A 可将正有理数 x 精确归一为 `x=2^k y，1≤y<2`，使 `0≤t<1/3`；这是减少求值范围，不是先把输入舍入到某张表。
【设计推论】取 N≥1 项和 `A_N=2Σ(j=0…N−1)t^(2j+1)/(2j+1)`；非负尾项可界为 `0≤R≤2t^(2N+1)/((2N+1)(1−t²))`，全用有理数计算。
【设计推论】ln 2 以 t=1/3 同样求正下界 L₂、上界 U₂；若 ln y 的界为 L_y、U_y，则 log₂ x 在 `k+[L_y/U₂, U_y/L₂]` 内。
【设计推论】将区间传播到指定取整出口，只有上下界 floor 相同才确定整数结果；x 为精确 2 的整数幂时直接返回 k，避免对精确边界无谓收缩。
【设计推论】这给出了可审查的误差方向，尚未给出所有合法输入的终止／资源上界。靠超时选近似值或加 epsilon 都不成立；下一包须限定已获准输入域并证明边界处理。
【设计推论】B 可以冻结查表／多项式及全套整数求值顺序，但必须同时冻结误差界；若区间跨越 floor 边界，需要已规定的精化规则，不能默认误差足够小。
【仓库事实＋待验】G01 的 `floor(20×(3/4)²×(1/2+log₂3/2))=14` 是已有见证；候选应证明取整前值处于 [14,15)，本次没有运行区间计算器。

## 6. 仅比较两个公开定义的 PRNG

以下公式是供核对完整状态与转换顺序的紧凑释义，不是待拷入工程的实现。两者都不承担 GrantId、认证、服务签名或安全令牌的不可预测性要求。

| 候选 | 主源定义与状态 | 本项目取舍推论 |
|---|---|---|
| PCG32 XSH-RR | 64 位 state 加奇数 inc，输出 32 位；原作者提供初始化、逐步转换和有界整数采样。[原作者源码](https://raw.githubusercontent.com/imneme/pcg-c-basic/master/pcg_basic.c)，核查 2026-09-17 | 两个状态字且有明确双参数初始化，适合先做小型移植向量核对；这不是性能或独立流统计质量的实测结论。 |
| xoshiro256** 1.0 | 四个 64 位状态字，不允许全零；输出 64 位，原作者给出转换与跳跃函数。[原作者源码](https://prng.di.unimi.it/xoshiro256starstar.c)，核查 2026-09-17 | 可将完整四字初态直接作为验证输入，暂不引入第三个种子扩展器；若产品只给单 seed，仍需另定映射。 |

【主源释义】PCG32 中所有状态算术模 2⁶⁴，输出算术限 32 位：保存 old=state；令 `state=old×6364136223846793005+inc`；`x=uint32(((old>>18)^old)>>27)`，`r=old>>59`，输出 x 右旋 r 位。[PCG 源码](https://raw.githubusercontent.com/imneme/pcg-c-basic/master/pcg_basic.c)，核查 2026-09-17。
【主源释义】以 a、b 两个无符号 64 位输入初始化：state=0，inc=(b<<1)|1；调用一次 next；state+=a；再调用一次 next。两次初始化调用属于固定协议，不能在恢复状态时再做一次。[PCG 源码](https://raw.githubusercontent.com/imneme/pcg-c-basic/master/pcg_basic.c)，核查 2026-09-17。
【主源释义】xoshiro 的输出为 `rotl(s1×5,7)×9`，先保存 `t=s1<<17`；依次 `s2^=s0; s3^=s1; s1^=s2; s0^=s3; s2^=t; s3=rotl(s3,45)`。各字算术模 2⁶⁴，右旋／左旋由固定 64 位移位合成。[xoshiro 源码](https://prng.di.unimi.it/xoshiro256starstar.c)，核查 2026-09-17。
【主源边界】PCG 作者不把其通常配置当强密码用途；xoshiro 作者明确其系列为非加密生成器。[PCG 可预测性说明](https://www.pcg-random.org/predictability.html)、[xoshiro 作者说明](https://prng.di.unimi.it/)，核查 2026-09-17。
【设计推论】任何候选进入正式设计前，都要固定算法／源码修订、整数宽度、溢出上下文、种子映射、初始与当前完整状态、字节序、流标识、每个合法事件的抽取次序。当前可变网页链接不是永久版本绑定。
【设计推论】流分离首先是独立持久状态与业务命名空间；不同 seed／inc 不自动证明业务事件互不干扰，更不能代替抽取顺序验收。暂不采用跳跃表来扩展本包范围。

## 7. 整数采样与概率量化

【主源保证】原 PCG 有界采样以阈值拒绝再取模，避免直接 `% bound` 的映射偏差。[有界采样源码](https://raw.githubusercontent.com/imneme/pcg-c-basic/master/pcg_basic.c)、[使用说明](https://www.pcg-random.org/using-pcg-c-basic.html)，核查 2026-09-17。
【设计推论】对 w 位原始字和 `1≤n<2^w`，令 `t=2^w mod n`；拒绝 r<t，否则返回 r mod n。被接收区间长度为 n 的整数倍，所以在原始字均匀这一条件下映射均匀；这不等于证明 PRNG 是独立真随机源。
【设计推论】n=0 必须拒绝；整个字域 n=2^w 须另有显式入口或表示。拒绝可能消耗多个原始字，不能只存“抽了几个奖励”推算随机位置。
【设计推论】若将两个 PCG32 输出拼成一个 64 位字，必须规定先高后低或先低后高、每次消费两个字及中途失败处理；不能把这种适配当原作者原生 64 位输出保证。
【设计推论】用 `T=floor(p×2^64)`、r<T 表示概率时，名义概率变为 T/2⁶⁴，通常不再等于 p；p=1 的阈值 2⁶⁴ 还不能装入 ulong。误差虽小，仍是规则内量化，必须显式审计。
【设计推论】若 p=a/b 且 b 可表示，可用无偏有界整数 r∈[0,b) 比较 r<a，避免这一阈值量化；但拒绝次数可变，需固定状态提交协议。p=0／1 是否仍取字也必须列入版本，不在研究中默定。

## 8. PRD 表与已定生命周期

【仓库事实】当前 PRD 模型按 `min(1,(失败次数+1)×C)` 求每次机会概率，通过等待次数期望的倒数匹配长期目标；20% 档的第一次机会不是 20%，而约为 5.57%。见 [calibrate.py](../../game-design/balance/calibrate.py)与[结果表](../../game-design/balance/results/prd.csv)。
【设计推论】“仍叫 20%”不足以兼容已有模型；须选择并记录 C 的精确表示、求参方法或冻结表、失败计数域、概率抽样器与强制成功边界。十位 CSV、二进制 float、固定整数阈值不是同一份定义。
【设计推论】量化 C 会影响每个失败层的概率，可能改变必出机会序号；应比较完整前缀概率、长期期望及必出位置。统计抽样只能补充解析见证，不能以一次命中率接近目标证明等价。
【仓库约束】正常新入场按绑定规则初始化；死亡／复活／Boss 翻面不重置 CD、PRD 或已用广告状态；完整撤回恢复目标历史中的随机／PRD，重来恢复原入场随机／PRD初态；广告资格切片另按历史设计核对。见[共同 §13](../2026-09-16/interaction-contracts.md)与[复活及历史](../2026-09-16/details/battle-history.md)。
【仓库约束】非法动作、预览、动画和未实际发生的尸体第二发不推进随机；掉落、奖励倍数与局内随机分开。上述条件约束任何候选，不能因实现便利新增抽取事件。
【仓库约束】第一次奖励抽取前必须已有持久依据：入场保存 Attempt 奖励依据、基础结算保存加倍依据，或先持久保存独立固定方案；失败、未知、换 OperationId 或崩溃不能重抽同一业务结果。见[共同 §13](../2026-09-16/interaction-contracts.md)与[结算设计](../2026-09-16/details/settlement.md)。
【设计推论】随机前态／后态、PRD 计数、被消费事件与结果须能一起核对；没有完整状态的 seed、只存 PRD 目标率或仅保存最后一个随机数都不足以重演。
