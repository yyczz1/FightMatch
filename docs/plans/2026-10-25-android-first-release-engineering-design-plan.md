## 2. 首版已经确定的范围

首版面向海外 Google Play，主要为 13 岁以上青少年和成人；具体国家／地区未选。游客普通玩法与本地存档为基础，保留主动激励广告、最小广告服务、小启动包首次下载主要内容，以及免费完整默认攻略。它不是完全离线、无服务的产品。

- **章节与职业：** 首章 1～16 关，战士初始拥有，法师在第 8 关通关后加入、从第 9 关参战；盾骑士第 21 关、弓手第 37 关，均不进入首章生产与验收。每职业一个角色、队伍最多三人。
- **装备范围：** 当前“装配”指职业战术道具的一槽一叠、战前补充与战内消耗；永久装备／强化仍延期，不因已有 `Equip` 命名就加入一套永久装备系统。数量上限、开关记忆、回退返还与来源扣减沿已定规则。
- **教学与 Boss：** 首次进入 16 关发通用职业之证，满足等级后由玩家确认学嘲讽、看用途说明，再开战；16 首通奖励的另一枚证单独记账。经验不足可回地图补级、返回继续，教学永久进度不随战斗回退。Boss 必须整面完成才翻面，不要求铺满棋盘。
- **数据与 UI：** Excel／CSV 是人工编辑权威源，Luban 做制作阶段生成，接现有校验／不可变发布。运行时 uGUI、英语与简中、系统默认及手选记忆、诊断占位符、项目自有本地化绑定、YooAsset 均已定。
- **联网与平台：** R2 Standard＋Cloudflare 缓存／CDN 路线已定；移动数据每次先显示剩余量并确认，Wi-Fi 中途转移动数据同样暂停等待。需重启的新版本在地图等自然边界提示、可稍后。Unity 保留 2022.3，2022.3.62f3 只是待验证候选；Mac Intel 与 Windows 保持同项目／版本。最低 Android 7/API24 已定。
- **广告：** 先接 AdMob＋Google 单一来源；Go＋sqlc＋MySQL 社区版的最小后端。没有批准第二广告源、开屏／插屏或完整账号后台。

正式 Google／邮箱账号、云档、人工申诉、当前战局在线分析均后置。保留既有契约和来源身份的扩展边界，不预建完整系统。游客本机凭据全失无法找回，须提前告知；恢复码、手动备份或匿名游客人工找回不加入首版。

## 4. 五个设计包与交付顺序

设计包按一个可评审结果组织，不预先拆成几十个实现包。每包的“验收”先指设计是否具体、是否覆盖必要例子；未来执行这些测试／设备／服务动作要另有实施范围和资源上限。

| 顺序 | 设计包 | 交付负责人／协作与接收 | 前置与输出 |
| --- | --- | --- | --- |
| D1 | 首章规则与永久状态 | 主程负责技术；主策负责规则／数值；主美补表现约束；主测试接验收案例；中央收产品取舍 | 现有规则与代码差异已知，先交能力清单、状态归属、版本／兼容方案和三个具体贯通例子 |
| D2 | 全内容表与发布 | 主程负责工具／发布设计；主策拥有表内容；主美拥有资源清单；主测试接生成／绑定验证 | 可先盘表，正式 schema 随 D1 收口；交表结构、生成适配、诊断和首章发布样本方案 |
| D3 | 真实资源下载与启用 | 主程负责；主策定已有流程的双语文案；主测试接网络／设备案例；中央协调账号／费用 | 依赖 D2 的内容身份／版本边界，可与 D1／D2 独立设计网络状态；交 R2 对象／缓存／启用合同及真实验证方案 |
| D4 | 单源广告与最小服务 | 主程负责客户端／后端设计；主策给奖励报价配置；主测试接故障案例；中央协调账号／预算 | 依赖 D1 的权益使用及 D2 的报价版本；无需等待完整账号。交客户端状态图、API／数据库草案、可信核验和部署候选 |
| D5 | 正式发行准备 | 主程负责技术组合；主策／主美准备商店与最终内容；主测试负责发行验证；中央接里程碑与用户决定 | 可先列兼容风险；最终矩阵依赖 D1～D4 的版本和所选地区。交可执行发布／回退方案及材料缺口 |

### D1：首章规则、职业、装配／制作、教学与 Boss

**拟定方案：** 保留现有 QFramework 应用组织、uGUI 控制器及唯一业务提交链。按实际支持域增加首章所需规则，不去掉支持域检查后假称支持所有职业。共享的状态字段可预留既有扩展边界，但不实现／发布盾骑士和弓手玩法。

输出包含：

1. 首章能力矩阵：战士／法师普通攻击与被动、嘲讽／火球、道具／制作、技能学习、CD、Boss 近远程／上弦／翻面，对每项标明复用、规则扩展或仅缺内容。区分永久学习、可回退战局、玩家记忆偏好、广告权益账本和表现临时态。
2. 一次有效行动的完整顺序与数据合同：普攻／道具、被动、技能、适用持续效果、敌行动、回合结束／补线；CD 只在已定有效回合推进，施放当轮不自减，补线／翻面／等待／表现不推进。按首章需求实现效果，不为后续弓手／盾骑士提前生产内容。
3. 16 教学状态图：未领取→已领取→等级符合／需补级→已学嘲讽→用途说明确认→允许入场。礼物、学习扣证、说明、首次通关奖励分别使用稳定身份；同一步重试、退出重进不重复发放／扣除，返回刷级后能继续。
4. Boss 两面及恢复合同：固定阵位、合法目标、法师优先远程与嘲讽改向、满血上弦不耗次数、所有必要线完成后换面；火球保留原中心／邻位定位，中心先死不挪目标。全灭救援、未完敌回合、回退／重来、PRD／CD／效果跨面延续须与既定规则一致。
5. 持久化增量和兼容提案：在旧 L1 档、活动局、待结算与新章配置之间逐类说明能否继续、何时迁移、何时拒绝并保留原档；不悄悄改现有格式或让旧局绑定最新数值。

**设计验收：** 主策与主程能用同一规则逐步走通三例：6～9 关同厚甲的战士／法师对照；16 入场赠证→不足等级回刷→回来学习→开战；两面 Boss 含一次上弦和回退／恢复。列明预期状态、库存／证书数量、行动事实及重启后状态，不把旧离线算例当运行通过。未来只对新增规则和受影响保存边界安排必要自动检查，实际教学／表现用真实页面验证。

### D2：Excel／CSV → Luban → 正式内容发布

**拟定方案：** 复用已安装的 Luban 文本路线和普通导表方式，扩展内容 schema；人工只改 Excel／CSV，生成 JSON／二进制是可再生输出。保留现有内容校验、指纹、不可变发布、旧局精确绑定与默认攻略验证，不再造第二套手工 JSON 权威源，也不把历史验收专用编译器流程扩成日常制作框架。

输出包含：

1. 关卡／多面棋盘／端点与默认路径、职业成长／技能／敌意图、战术物品／配方、解锁／奖励／教学、文本及资源 ID 的表关系；明确稳定键、版本、引用、单位、坐标原点、空值、列表和跨表错误定位。
2. 精确数值映射：Excel 显示不改变计算语义，数值进入既有精确表达／预算校验；随机和规则版本随发布固定。禁止用浮点格式化悄悄改变旧值。
3. 生成与发布责任：策划／美术编辑源表和资源映射→Luban 生成→适配现有模型／验证→生成不可变内容集合与清单→供 YooAsset 构建／D3 分发。先验证引用与能力，再允许发布；缺能力、重复键、断引用、错语种参数或无有效默认攻略应给到表／行／字段诊断。
4. 首批制作样本先用现有 L1 做**格式迁移对照**，再覆盖 8／9 解锁与法师、16 教学及两面 Boss；这不是重跑 L1 全套。之后同 schema 填齐 1～16 关，完成完整几何及默认攻略，不要求唯一解、不要求满盘。
5. 固定工具版本及 Mac／Windows 相同输入的输出规则、生成目录、资源／meta 生命周期和发布回退方法。优先复用当前 Luban v5.1.0 基线；若具体能力不足，技术设计提交必要版本差量，不重新询问是否采用 Luban。

**设计验收：** 一份实际字段样表能追到发布模型和读取入口；正常与错误样例都有确定结果；文本参数一致、生成可重复、相同旧局引用不漂移。主策确认首章内容覆盖，美术确认资源 ID，主测试接生成差量、旧局绑定和默认攻略验证。完整章节跑通与美术效果属于后续生产验收。

### D3：R2／YooAsset 真实下载、续传和版本启用

**拟定方案：** 用现有 AssetAccess 契约与 YooAssetAdapter 接真实传输，保留 Host 的单次启动 owner／epoch、终止等待和资源激活记录。R2 是已选对象存储，广告业务服务器另选；不重新比较 CDN 厂牌。

输出包含：

1. 小启动包与主要内容边界；资源集合、平台、内容指纹、清单及对象路径的不可变身份；可信引导清单从何获得、怎样校验、兼容失败如何保持旧集合。客户端不得包含 R2 上传管理密钥。
2. 所选 YooAsset 版本的真实下载适配、缓存根、半文件身份、续传阈值与校验时机。当前 lock 已固定 3.0.6 对应提交；[旧续传研究](../system-design/2026-09-17/yooasset-download-resume-research.md)中的“尚未安装”已过时，其 API／Range 结论仍需按实际包和服务配置复核。
3. 首次缺包阻止业务启动、完整有效缓存可离线、取消／重试／进程重开、空间不足及损坏的状态图。精确剩余量来自当前下载计划；取消必须等该次传输／清理完成才重绑，不把“发出取消”写成“已经停净”。
4. 所有首装／更新／按需入口共用 Q35：将使用移动数据时先暂停、展示剩余量，收到本次确认才继续；Wi-Fi 切移动数据使旧许可失效并再确认。说明在途请求如何停止及字节如何观测，不承诺底层瞬时零字节。
5. 下载完成、内容验证、可用集合和业务准入分离；需重启的版本只在自然页面边界提示，可稍后。活动局继续绑定原内容；禁止半包启用、删除唯一可用旧集合或靠新版本覆盖解决保存冲突。明确 HybridCLR 后续热更新与原生 SDK／AAB 更新的界限，不假设现有包已完成热更新发行验证。

**设计验收：** 给出真实 R2／CDN 的后续验证矩阵：首次下载、有效完整缓存复用、半文件中断／冷开、206／忽略 Range 的 200／416、对象变化／损坏、存储不足、Wi-Fi→移动数据、拒绝／确认、重复重试、下载完选择稍后、旧局续玩。服务与设备实测须记录实际请求／字节／版本；本机 Fake 或已有离线启动通过不能代替这些结果。

### D4：AdMob 单源与 Go／sqlc／MySQL 最小广告服务

**拟定方案：** 只为游客激励广告建立可认证的设备凭据及奖励账本，不建设正式账号／云存档。Unity C# 继续负责现有精确玩法；服务端负责可信广告完成、奖励报价、去重和领取恢复，不重写整个战斗模拟器。

输出包含：

1. 已批准广告用途与版本化报价表：材料／经验卡／直接经验、复活、手动通关机会及结算增益，按各自原范围接入；首版不接在线局面分析。具体数量／可用时机由主策提交配置，沿已有决定，不新加自动广告或囤积入口。
2. 最小链路：游客凭据→请求已发布报价→SDK 展示→服务端核验完成事实→持久收件／唯一事实→客户端查询和领取→本地业务原提交链幂等兑现→确认。客户端 SDK 回调、文件哈希或任意奖励数值不能独立成为可信发奖依据；服务端校验方案、失败状态和签名／密钥轮换要在选定 SDK 的官方机制上具体化。
3. 数据与 API 草案：游客主体、报价／广告会话、平台交易去重键、原始核验收件、不可重复的权益／领取记录；MySQL 唯一约束／事务和 sqlc 查询明确到并发重复、超时、重放、回执迟到与崩溃后的结果。API 超时后能查询原请求，不靠重新展示广告恢复已经取得的权益。
4. 客户端账本边界：已核验广告事实不因回退／重来／退出／换关／迟到而删除；使用与撤回有唯一身份，复活不能重复免费使用；通关机会需原关卡、合法尝试及教学准入，不能绕过 16 教学。来源先扣广告再普通；16 入场教学证与首通证分开，后者不重复发。
5. Q1／Q2／Q5／Q18 的跨档规则作为未来兼容约束保留来源、原物和职业身份，不在本包实现合档／云档；本机凭据全失不能承诺找回。后端部署候选给出限定负载、备份／恢复、日志保留、监控和维护责任及费用估算，交中央汇总选定预算和提供商后才可操作服务。

**设计验收：** 对一份广告分别走通正常发奖、客户端先退出、服务端回执迟到、重复回调／领取、收件持久化后进程中断、本地保存成功但确认丢失、回退撤回一次使用、重复首次通关证和游客凭据丢失。每例写明广告事实、可用权益、已用记录及本地业务结果；不得两边都发或丢失已取得权益。后续先用平台测试广告和受控服务验证，再按独立发行安排接生产账号；本计划不购买／部署。
