## 1. 为什么 QFramework 和规则会同时出现

**整个 Unity 客户端仍然使用 QFramework。** QFramework 的 System 负责组织业务操作，普通 C# 对象负责执行具体规则。这些对象可以直接被 System 调用，不必先包装成另一套框架，也不要求每个对象都创建接口。

例如，棋盘把完成的连线作为 Command 发给 BattleSystem。BattleSystem 找到当前 BattleSession 并调用 ApplyAction；BattleSession 完成路径、攻击、技能、道具和敌方阶段的规则计算，返回结果；BattleSystem 发出事件，Unity 表现层更新棋盘、端点、血量与动画。

独立的是代码依赖：战斗规则不引用 QFramework、MonoBehaviour、GameObject、广告 SDK 或网络。在线攻略搜索和编辑器验证便可以创建自己的对局实例，使用相同的规则与数值。图里的“共用”不表示几个程序共用玩家手机中的同一个对象。

规则独立也不意味着所有业务都搬到独立库。UI、页面导航、存档、广告、网络和客户端流程仍归客户端；影响战斗结果、需要跨环境重演的规则才是共享部分。

## 3. 模块职责与状态归属

| 模块 | 候选 QFramework 入口 | 规则与数据 | 边界 |
| --- | --- | --- | --- |
| 页面与战斗表现 | 各页面 Controller、Command、事件订阅 | 选关地图、冒险/队伍/背包入口、棋盘与头像 | 表现不直接计算伤害或发奖；两个端点读取同一个敌人的生命 |
| 角色、成长、阵容、局外恢复 | CharacterSystem | CharacterRecord、FormationState、GrowthRules、RecoveryRules | 等级、经验、技能解锁、最多三人顺序是局外状态；局外恢复传入当前时间计算 |
| 装备、背包、固定配方 | EquipmentSystem | InventoryState、ItemStack、TacticalLoadout、EquipmentRules、RecipeDefinition | 装配和整理不改变总数量；一个战术槽装一叠职业可用物品 |
| 对局与回退 | BattleSystem、BattleModel | BattleSession、BattleRules、BattleState、BattleHistory、ActionRecord | 当前战斗状态只由对局持有；回退到目标行动前并撤销其后全部敌我行动 |
| 职业与技能 | CharacterSystem 管理解锁，BattleSystem 调用规则 | ProfessionDefinition、SkillDefinition、SkillResolver、具体效果 | 区分被动触发与专属技能施放；概率与 CD 规则属于配置，运行状态属于对局；CD 口径待确认 |
| 配置目录 | ConfigSystem（候选） | ConfigCatalog、HeroLevelStatsRow、EnemyDefinition、EnemyStatsRow 及技能/物品/奖励配置 | 加载、校验、提供指定版本的只读配置；规则直接接收数据，编辑器与在线攻略读取相同版本 |
| 关卡与解锁进度 | LevelSystem | EncounterDefinition、PlayerState.stageProgress | 普通连续关可沿用阵容直接开始，准备页按需进入 |
| 胜利结算 | SettlementSystem | RewardCalculator、SettlementResult | 统一入账经验、掉落、进度和实际战术物品消耗；界面只展示结果 |
| 完整攻略与权益 | HintSystem | IBattleGuideProvider、BattleGuideRequest、BattleGuide、BattleGuideVerifier、HintAccessState | 在线计算与离线参考是不同来源；内容有效后才消耗权益 |
| 广告、网络、存档 | RewardedAdSystem 与接入类/Utility | AdCompletion、RewardedAdGateway、PlayerSaveUtility | SDK 只返回完成结果，业务系统决定效果；供应商、协议、格式尚未选定 |
| 编辑器扩展 | Editor 工具，不强制套客户端 System | FightMatchEditorExtension、FightMatchLevelAsset | 基础几何编辑器独立保留，RPG 配置通过明确扩展入口接入 |

### 只读配置与两种状态，避免重复维护

ConfigCatalog 持有职业等级属性、技能与触发条件、敌人数值、物品、配方和关卡等只读定义。配置不保存当前生命、PRD 积累或剩余 CD；逻辑表及引用关系见新增对齐清单第 3 节。

PlayerModel 持有 PlayerState。PlayerState 拥有角色记录、背包、阵容、关卡进度和提示权益；角色记录拥有其战术装备装配记录。库存与槽位中的数量都是真实已有物品，总量守恒。

BattleModel 只持有当前 BattleSession。BattleSession 拥有 BattleState 与历史；BattleState 拥有本局生命、倒下状态、敌方意图、护盾/嘲讽/中毒、固化线、随机状态、PRD、贡献、待结算收益及战术装备剩余量。若采用技能 CD，各角色的剩余 CD 同样归这里并随历史回退。只读 UI 数据可以投影出来，但不能成为第二个可独立修改的生命或道具账本。

开战时从角色等级、职业、解锁技能、装备和关卡配置建立对局初始数据。配置与规则版本也随攻略请求记录。成长规则会影响战斗属性，但升级动作本身属于局外业务。

### 战术物品跨越两个模块时怎样处理

1. 背包不限制总格数，可堆叠物品统一每叠 99 个。出战前，EquipmentSystem 按现有库存自动补充：角色剩 2 把、背包有 99 把时，角色带 99 把，背包剩 2 把。
2. 入场保存起始装配数量，创建 TacticalStackState。战斗内使用道具只减少对局剩余量，不让每次出手直接修改长期库存。
3. 撤销恢复行动前数量；重来或结束失败尝试恢复入场数量，本次经验与掉落不保留。恢复数量与下次出战补充是两个步骤。
4. 正常胜利（含广告直接通关）按本次实际使用量更新局外装配记录。五把入场、实际使用两把，只扣两把；跳过的后续行动不虚构额外消耗。

最新首版范围仅为职业专属消耗品，永久武器、护甲及强化延期。缺货仍保存装配物品 ID 和数量 0，允许开战；重新获得物品后再自动补充。目录分类、排序与分页已定，后续补页面衔接和正式配方内容。

失败后观看广告继续同一次尝试时，返还数量与已有行动记录如何衔接仍需明确，列为 C09。这不改变策划已明确的失败返还规则，也不能由实现方自行选取能重复刷物品的口径。

## 4. 核心设计建议及其依据

**职业先按组合方案讨论。** 共用角色实例结构，搭配 ProfessionDefinition 与具体技能效果；无须因为有战士、法师、弓箭手、盾骑士，就先规定四层继承关系。若之后出现无法由相同生命周期表达的职业行为，再针对实际差异决定拆分。

**接口用于真实变化点。** 攻略有在线与已保存两种来源，所以 IBattleGuideProvider 有直接用途；伤害、嘲讽、护盾是不同效果，所以 ISkillEffect 有明确候选实现；基础编辑器需要保留通用用途，同时接入 RPG，因此讨论一个编辑扩展入口。BattleSession、RewardCalculator 等稳定入口暂以具体类表达，不给每个类机械添加一个 I 开头的接口。

**行动规则和动画分开。** 一条完整合法路径在松手时提交，思考与拖动不推进战斗。验证需考虑当前战术物品赋予的有效射程与剩余数量；无效行动不能扣道具或推进随机。攻击与技能分别判距，只能施放技能时仍可形成一次行动。玩家结果已获胜便不再推进敌方阶段。

**历史先保证正确性。** 图中用“行动前完整快照”解释回退范围；这不是已经选定的最终存储结构。快照、增量或重演的选择需用实际局面验证内存和耗时。不能为缩短记录、搜索或评分计算而暗加玩法不允许的回合数与贡献上限。

**搜索用规则验证，不用几何解替代胜利。** 在线搜索尝试角色、目标、路径及顺序，使用独立的 BattleSession 副本。相同起点、规则/配置和随机状态应得到相同结果。是否能证明无解，取决于搜索空间与终止条件；超时只表示尚未找到。离线参考也要明确阵容、等级、装备等适用条件。

**广告效果由相应用例提交。** 先完成内容/目标有效性检查，再请求广告；失败或取消不产生已领取状态。SDK 回调不直接改生命、发经验或写存档。重复回调与结算重复执行应在接入/用例边界避免重复入账，具体持久化方案尚待选择。

## 7. 建议的下一步

将[玩法依赖清单](2026-09-15-planning-alignment.html)交给策划任务讨论，避免在两个会话重复询问。架构会话继续模块职责、数据归属与接口的技术讨论；有明确玩法依赖的细节保留待定，收到策划确认结果后更新类图和时序。

等局外与核心战斗规则补齐，再逐模块细化 UML、完善分支与事件时序，做策划/架构交叉检查，形成可批准的架构稿。获准后才拆外部实现任务包，明确文件白名单、验收场景和验证步骤。
