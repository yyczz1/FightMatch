## 更新顺序

1. 核对用户的新决定、相关策划和代码，区分已实现、已确认、候选与未决内容；当前架构状态以讨论稿为准。
2. 修改架构说明及受影响的 JSON / Mermaid 图源。同一个类在不同图中使用一致名称，状态归属与流程保持一致。
3. 从图源重新生成 HTML / SVG。直接修改生成图不能替代源文件修改，避免下次生成丢失变更。
4. Archify 依次执行 `validate`、`deliver`、`visual-check`，再检查实际截图。Mermaid 使用 [本地生成器](2026-09-14/uml/render.cjs)生成，并检查明暗主题、箭头、文字和链接。
5. 更新关联入口与验证记录，使收据、截图和当前产物对应。图稿验证与 Unity 编译、游戏测试分别记录。

## 讨论顺序

当前会话先确认系统职责、状态所有权、依赖方向及跨系统协作，用入场、行动、回退和结算等场景检查多系统冲突。系统接口细化与设计方案移交后续系统设计会话；字段、方法、算法及具体系统执行由各自会话处理，不以完整类图作为本层完成条件。

用户主要审阅图稿和确认设计取舍；Codex 负责维护源文件、生成阅读版和执行图稿检查。

会话分工：玩法规则、职业技能、CD、毒与平衡数值由策划任务「规划游戏后续开发」和用户讨论；本架构会话接收规则，负责整体职责、状态归属、系统协作与跨系统约束。后续系统设计不得擅自改变这些共同约束，发现影响多个系统的问题须返回架构评审。各会话不重复追问已定玩法。

本地生成器需显式提供 `--mermaid`、`--playwright`、`--chrome` 以及 `--marked` 的已安装文件路径；`--marked` 指向现有 runtime 的 `node_modules/marked/lib/marked.esm.js`。`--verify` 指定截图目录。不会向 Unity 项目安装 npm 依赖。
