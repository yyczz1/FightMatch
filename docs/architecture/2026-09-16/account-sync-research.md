# 账号、云存档与跨分支广告权益研究

2026-09-17 · r4 · **架构研究与建议，未选定供应商，未授权实现。** 已确认一次广告机会使用时联网校验、普通闯关和养成离线可用、独有广告直接收益及转化结果跨档保护。本轮进一步确认同一张已领广告卡发生分歧消费时只保留所选档的一种结果，见第6.3节；后续普通闯关成果仍按普通选档处理。下文B保留为未采用的比较，不再是待答问卷。

建议采用“本机完整保存＋账号下的局外检查点＋独立保护的广告凭据”三部分。普通进度按共同祖先识别分歧，由玩家选一份；账号后端管理身份关联、条件提交和跨分支权益核对。现有单机完整提交继续承担离线游玩与本机续局，不把云端当成每次行动的前置。

这些决定已形成[共同交互扩展H11～H14](../../system-design/2026-09-16/runtime-extension-contracts.md)，但**不能据此宣称已实现全局一次使用，或完整保护所有已转化收益**。联网许可、效果提交、撤回已有阶段与完成条件首稿；来源粒度、混合合成和设备丢失等仍有具体缺口，见[独立审查](../../system-design/2026-09-16/ad-reconciliation-review.md)。

## 2. 最小职责与信任边界

| 部分 | 唯一职责与边界 |
| --- | --- |
| M02应用流程及各业务负责者 | 组织完整本机提交、生成可同步检查点、展示选档差异并应用明确选择。成长／库存／进度／结算仍由原负责者校验和计算；同步层不自己算经验、解冻、发奖。 |
| M12本机保存与平台接入 | 保存完整业务版本和同步待办，承接认证／云端传输及原始广告证据。延续本机Completed、CommitUnknown、Lookup语义，不把上传成功冒充本机已安装新档。 |
| 账号与同步服务（新增逻辑职责） | 维护游戏账号与认证身份映射；授权读取；以期望云端头做条件提交；记录绑定／选档／权益操作的稳定结果；保护跨分支凭据并返回核对结果。它可在一个后端部署，不必拆微服务。 |
| M08权益与M07结算的云端核对边界 | 定义事实、Grant、准确Use／撤回、固定发放效果与归属；服务端只接受具备相应依据的状态转移。平台SDK回调和客户端上传的“我已看完／我已使用”不是同一种证据。 |
| 身份提供方、广告提供方、内容分发 | 身份提供方证明某认证主体，广告接入给出其实际支持的完成证据，内容服务交付版本。三个服务均不决定玩家选择哪份普通进度，也不自行重写业务档。 |

推荐游戏账号使用独立`AccountId`，保留现有本地`PlayerId`／本地资料身份作为来源，不用设备号或某平台用户ID替换全部业务身份。外部身份键应包括提供方、应用／租户作用域和该作用域内主体；具体微信作用域须先通过官方资料与接入实验核实。关联只能基于认证证明或双端明确授权，不能以昵称、头像、职业相同推断同一玩家。

后端能保护已接收的云端头、身份归属和操作去重；它不能仅凭客户端快照证明所有离线战斗真实发生。文件摘要发现损坏，不创造广告完成证据，也不构成反作弊。未上传的离线资料仍只受本机保存故障模型保护。服务端可信时间可用于已在线确认的事件，但不能把设备离线时间伪装成服务器时间。

## 3. 三类资料，四种广告含义

| 资料 | 应包含 | 不可混淆的完成点 |
| --- | --- | --- |
| 本机完整版本 | 永久资料、活动尝试、完整回退历史、冻结、当前偏好、请求／事实／使用、待结算、操作结果和同步待办。 | 本机持久成功只证明本机版本完成；断网也可继续正常业务。 |
| 可同步局外检查点 | 一份自洽的角色／库存装配／进度教学／恢复状态，必要的已完成结算与唯一业务键，内容及格式版本，源分支、共同祖先和所对应权益视图。 | 后端接收一个局外检查点，不表示另一设备已经安装，也不代表源设备活动战斗已结束。 |
| 跨分支保护凭据 | 广告原请求与核验依据、Fact、Grant、Use／准确撤回、已兑现效果及必要结束／结算凭据、原对象和来源资料身份。 | 收到事实、获得资格、效果落入业务版本、可在当前上下文使用，四者分别确认。 |

广告含义必须分开：

1. **事实**：一个原请求有一次可核验的完成；跨设备重复传输仍是同一个Fact。
2. **资格**：该事实产生哪个用途、哪个角色／关卡／结算的一次Grant；不因选档丢失。
3. **兑现效果**：哪个Use在什么业务提交中实际复活、结束恢复、交付分析、追加固定经验／物品或广告通关；不能只存`used=true`。
4. **当前可用性**：还未使用、目前有合法目标、按用户已选A是否取得联网许可、是否正在核对；“暂不可用”不能偷换成“资格被删除”，也不能把“资格存在”显示为已到账。

保护凭据可以在无关普通分支之间保留事实，但不是简单集合并集。相同Grant的两个未撤回Use构成冲突；针对U1的撤回不得释放U2。已交付攻略与未交付服务、已发永久收益与尚待兑现资格，也不能统一为一个可相加余额。必要的使用／结束凭据允许跨设备防重，不等于上传可供续局的战斗快照或回退历史。

## 4. 进行中战斗与冻结：最小检查点建议

**建议首版只在无活动尝试且没有未完成基础结算的边界发布新的普通局外检查点。** 开战后云端可继续提供上一个完整局外检查点；本机每一步照常保存，另一设备不接续该战斗。结束联合提交完成后，新的局外版本才具备发布条件。后续若希望同步战斗期间到账的永久成长，须另行证明投影一致性，不能在首版顺手剪字段。

例：本机原有总量T=5，局外分配L=2，可用F=3。入场后T=5、L=0、冻结R=2，战斗用掉1件，余量U=1。此时不能删除战斗和R，直接把T=5、L=0、F=5发给云端；那是没有业务结束凭据的释放。也不能先把T扣成4，假装未完成战斗已经结算。上一局外检查点T=5、L=2、R=0、F=3本身自洽，并且明确属于开战之前；原设备的冻结和消耗仍保存在原完整版本。

另一设备从旧检查点继续，可能再次使用这些普通资源；这属于用户已接受的离线普通分支分歧，之后选档，不能称为两边资源合并成功。原设备战斗继续／结束后仍在自己的分支上提交，不因另一设备上线自动变成失败、退出或重来。

广告事实可先上传保护；但战内Use、撤回与晚到永久收益必须携带它们属于哪个本机版本／业务对象的凭据。普通检查点滞后时，不能以“新广告账＋旧普通档”组成一个可立即花费的混合版本。例如新账已用、旧档未含发物，必须表明效果尚未投影，而非据此认为收益已经送达另一设备。

远端选择也不能覆盖本机仍活动的完整存档。推荐保留原分支及活动尝试，将导入安装安排在安全业务边界；若源尝试继续产生新普通结果，仍按真实分支关系再次核对。此处是保存／应用策略建议，不是强制单设备，也不是未经玩家选择终止本局。SD02／SD06／SD08／SD11必须明确检查点生成与安装时点、待结算优先恢复、晚到权益和分支展示。

## 5. 游客绑定与普通冲突

推荐游客第一次游玩只创建本地资料，不把在线匿名认证成功作为开玩前置。绑定时先验证目标账号并保存稳定`BindOperationId`，冻结本次导入描述及摘要；后端回答可查询的结果后，本机再持久安装关联。网络结果不明期间保留游客原资料和原绑定操作，不重新生成导入身份。

| 目标情况 | 建议处理 |
| --- | --- |
| 账号没有普通进度 | 接入游客的可同步检查点及保护凭据，保留来源身份；不重发首证、首通或广告收益。 |
| 账号已有普通进度 | 读取两侧差异，让玩家选择普通进度；同时独立核对所有保护凭据。选择哪份进度不等于授权抢占别人的认证关联。 |
| 原游客有进行中战斗 | 仍按第4节接入最近可同步检查点并保留本机续局；不能把绑定视作整场结算。后续完成可能形成新分歧。 |
| 绑定回执丢失、重复点击 | 查询原操作；同意图返回同关联及导入结果，同ID不同意图拒绝。未查明前不删来源资料、不再导入一遍。 |
| 原游客广告晚到 | 继续定位原请求及原业务对象，经保留的来源到账号关系接入；不得因`PlayerId`变了另造Fact／Grant。 |

绑定与导入不是同一个原子动作的当然事实。后端账号关联已成但本机尚未安装、进度选择已成但广告核对未完成，都需要明确阶段及查询，不能用“登录成功”覆盖它们。

还需细化：游客与已有账号各有一个“战士”，各自`CharacterId`不同；角色Grant如何映射到选择后的角色，必须保留来源并由成长负责者定义，不按显示名合并。Settlement／Challenge也不能只凭同LevelId视作同一个对象；固定旧奖励可能需要保留其原结算凭据，即使那侧普通成果未入选。

普通冲突识别建议用共同祖先／分支身份及云端版本，不用本机时间大小裁决。无分歧可推进，有分歧生成带两侧版本与摘要的选档提案；确认时再次条件检查。任一侧变化就重新展示，不把用户对旧差异的确认套在新数据上。至少显示关卡、角色成长、关键库存和广告核对状态；两侧只作可恢复证据保留，不提供任意读历史档刷收益的入口。

## 6. 已确认的取舍与未完成的收益核对

### 6.1 同一Grant跨设备离线兑现

**推论与反例：** 两端从同一已同步状态看到G未用，随后断网。A无法区分“B没使用”和“B已使用”；如果两端都获准立即产生效果，那么两次效果都可能发生。稳定GrantId、不同UseId、最终选档或后端去重只能事后识别，不能抹去已经发生的复活／养成体验。

以下保留两种策略及代价。用户已明确选择A，B未采用；确认的是使用体验，不是协议已经实现或通过验收。

| 选项 | 玩家可见行为 | 能保证什么／仍需什么 |
| --- | --- | --- |
| **A：用户已确认，普通游玩离线可用，广告权益兑现需联网核对** | 普通闯关和养成照常离线；已得权益一直保留，但断网时不能新兑现。联网后查询同一操作继续。 | 可把同一Grant的新使用许可交服务端排他裁定，缩小重复使用问题。需设计许可、业务效果、本机提交和服务端确认间的未决恢复；不能仅“请求成功就扣资格”。本机回退释放精确Use也需核对，超时不能假装未使用。已发入背包的物品正常消费仍属于普通离线养成。 |
| **B：广告权益也可离线先兑现，接受分歧期间重复效果的可能** | 两端离线均可使用当前本机认为可用的权益；同步后选一份普通主进度。 | 不承诺分歧期间全局最多一次效果；目标是最后主进度避免永久重复入账。仍须SD07／SD08设计冲突Use、精确撤回、效果归属与选择后的对账，不能把“选一份”宣称为已解决所有广告收益。须让用户明确接受该重复体验边界。 |

单设备许可、预分配离线额度或到期租约也会改变权益在另一设备的可用性，并需处理离线转移／过期后的旧许可，不能作为无代价第三方案偷偷加入。当前按A将新使用许可交联网权益流程，M06仍只计算传入合法操作的战斗效果。回退在本机完成，撤回记录待联网核对；同一机会再次使用须联网。游客校验凭据与正式绑定分别设计，不由本选择推导必须先注册。

**数值例（用于推演，非正式配表）：** G固定发3张经验卡，每张100经验。两设备共享“G未用、卡0”的检查点后断网。A以U1兑3张并全用于战士，得到战士+300、卡0；B以U2兑同一G并全用于法师，得到法师+300、卡0。选A后，普通主进度只保留战士+300；G记同一逻辑资格且不能再发3张。这个简单例中B的+300不进入主进度，但B确实已经体验过该效果，B策略承认这一点。仅将U1／U2取并集，会违反G只能有一个有效使用；只取余额最大值也无法表达谁使用了什么。

### 6.2 选档不能丢弃已兑现广告收益

A也没有单独解决这个问题：即使G只获准在A使用一次，玩家仍可能选择不含那次收益的B普通分支。必须把“防止第二次使用”和“选择后收益仍有所属”分开验收。

**用户已确认保护范围。** 在“A广告得3张卡、用2张给战士、余1张并随后普通通关；B未含此次广告收益，玩家选B”的场景中，用户同意保留B普通进度，加上A的剩余1张卡和2张产生的战士经验；A后续普通通关记录和奖励不合并。决定来源见[会话计划第16节](../../system-design/2026-09-16/session-plan.md#16-用户决定跨档保护广告直接奖励及已转化结果)。以下100经验数值仍仅为研究算例，不是用户批准的新配表。

沿用G的3张卡，改为仅A取得／兑现G：A用2张使战士+200，余1张；B有其他普通成长但完全不含G。玩家选B时：

- 只保留G事实和已用标记，会丢失其+200与1张卡，违反权益保护。
- 同时恢复3张卡并保留+200，会把3张的原价值变成5张等价量，重复入账。
- 在B中保留“G对应战士+200和1张卡”已成为此例的目标结果；仍须准确知道消费来源、哪些效果已包含在B、固定原增量，以及该结果如何与B合法组合。当前总库存和Use标记不能证明这些关系，不能覆盖整份A角色资料来代替核对。

同一广告卡分歧消费的取舍已由第6.3节补充；来源与结果的完整核对仍需证明。[正式主稿](../../game-design/2026-09-14-fightmatch-game-design.md)已包含广告普通材料和首版职业消耗品合成，因此混合材料并非纯未来假设；具体首章飞斧配方仍为候选，未做数值可达性验证。用户已明确广告帮助取得的后续普通闯关成果服从选档；不能将整条后继因果链都归入广告保护，也不能只保留广告事实便宣称保护了效果。

**最小设计方向：** 给固定永久广告发放保留来源份额、消费分摊、实际效果及原受益对象；SD03／SD04／SD08提供目标检查点已包含或已继续消耗的证据，耗尽不删除必要防重依据。SD07逐用途区分可恢复资格、已交付服务和已兑现结果，SD15组织核对；不能用余额或账号全局used推断目标档已收。具体追踪粒度、部分来源组合、混合消费及身份兼容仍待证明。

本轮确认保留实际直接奖励及转化结果，没有批准在不能组合时转换为等价补偿、再发原卡或叠加同源重复消费。若具体情况无法同时满足保护与防重，须先给出反例和方案，不能自行新增补偿或把普通用卡改成必须联网。技术核对未完成时保留两侧证据，标明未决，不自动确认一个声称无损的选档结果。

| 文档验收场景 | 已定预期或仍需证明之处 |
| --- | --- |
| B完全不含G，A用2张余1张且后来普通通关 | 保留B普通进度，接入G对应经验和1张卡；不并入A后续普通通关与普通奖励 |
| B已经含有同一G的相同经验和余卡 | 不再发经验或卡，不能仅因重新选档重复入账 |
| G的部分结果已在B，其余来自A | 只处理可证明缺失的结果，不以总等级或库存差额猜测来源 |
| 选档确认或本机应用中断后重试 | 查询并续办原操作；不重复发放，不在结果未确认时删去来源资料 |
| 同一已发广告卡在两端分别用于战士／法师 | 用户已确认只保留所选档的一种结果；另一独有广告来源继续保护，具体份额协议仍待证明 |
| 广告材料与共同普通材料混用合成 | 普通投入在两端争用时，保护混合结果可能改动所选普通成果；须给具体方案，不自动补偿、重复投入或扣其他材料 |

该表是设计预期，未执行游戏、云端或故障恢复测试。

### 6.3 同一张已发广告卡的分歧消费

用户已明确选择：**同一张卡同步到A／B，离线分别用于战士／法师，选A后只保留A中的一种结果。** 另一设备从不同广告独立取得的奖励继续按第6.2节保护。实际接收见[会话计划第17节](../../system-design/2026-09-16/session-plan.md#17-用户决定同一张广告卡的分歧消费只保留所选结果)。

最小反例是G已经联网正确兑现一次，之后同一已发卡随普通存档复制到A／B；两端消费无需第二次申请Grant。若相加两个转化结果，仍会复制来源价值，因此“Grant在线排他”和“已发物品最终选档防重”必须分别设计。该确认保证最终选择目标，不撤销离线期间已经发生的两次体验。

确认范围是一张卡的冲突结果，不是整个多张Grant强制整批选择，也不证明任意两份广告与普通材料的合成结果都能组合。详细设计须展示份额、包含／消耗凭据和固定候选如何支持这一目标；不把已经正常用完的来源当未领取，不把另一侧独有来源随普通分支丢弃。

## 7. 少量必要接口语义与后续验收

以下为逻辑操作，不规定HTTP端点、SDK、数据库表或新增C#类型。可以合并实现，但不能省略语义。

| 操作 | 最小语义 |
| --- | --- |
| `Authenticate / BindGuest` | 验证外部身份；返回游戏账号及关联状态；绑定带稳定操作、来源资料身份、期望账号状态与导入摘要。已有账号返回冲突提案，不强制重绑或自动合档。 |
| `ReadSyncState` | 返回普通云端头／检查点与其权益视图依据、兼容要求和必要保护凭据；不以分别读取的任意两个“最新值”拼一个可写状态。 |
| `SubmitCheckpoint / ConfirmSelection` | 提交本机已完成的局外候选，带源分支、祖先、期望云端头、选择提案及权益核对依据。完整条件满足才形成一个可查询的新云端结果；否则Conflict／Stale／ReconciliationRequired／Unsupported。 |
| `ReconcileEntitlements` | 接纳带原请求依据的事实与Use／撤回／效果记录，报告新增事实、已包含效果、矛盾和待核验项。不能等同于相加余额或自动发物。 |
| `AuthorizeEntitlementUse` | 按用户已选A联网核对，返回允许的准确使用、需在线、待核对或不适用；许可与本机效果之间的未决状态须可恢复。业务负责者仍校验合法目标。 |
| `LookupOperation` | 绑定、同步、选择、权益操作结果未知时查询同一意图的原结果；不以重建新ID代替解决不确定性。 |

后端已提交、本机未安装时保留同一云端结果及本机原分支，续办本机完整提交；本机已完成但上传失败时保留待办，不能回滚玩家已确认的本机业务。[H12／H13](../../system-design/2026-09-16/runtime-extension-contracts.md)已分出关联、选档、条件提交与安装完成点，后续由SD14／SD15和SD02／SD11细化；不能声称跨本机文件与远端数据库天然原子。

设计关闭前至少推演并在实施后验证：①开战后冻结与云端旧检查点；②WonPendingSettlement不上报已通关；③游客绑定已有账号、回执丢失及晚到广告；④相同G跨设备U1／U2及只撤U1；⑤选档未包含独有广告收益；⑥已兑现收益进入卡耗／合成／结算依赖；⑦确认差异后云端又变；⑧云端成功而本机安装中断；⑨旧规则／格式无法读取；⑩另一设备继续普通游玩时，原设备仍可本机恢复活动尝试。

当前均为**设计推演、NOT RUN**。第6节联网使用、独有收益保护和同一卡冲突裁决已由用户确认；SD00维护共同语义，SD14／SD15设计身份与同步，SD02／SD11对接保存和应用，SD03／SD04／SD07／SD08证明广告结果保护，SD06核对本机活动战斗及精确撤回。完整协议仍须关闭混合转换、身份不兼容与许可设备丢失场景；完成文档不代表微信接入或某云服务已经可用。

## 8. 官方能力研究及证据限度

### 已实际读取的官方资料

| 事实 | 对本项目的含义（建议／推论） |
| --- | --- |
| Unity匿名登录可创建玩家；未绑定且会话令牌丢失的匿名账号不可恢复。[Unity：Use anonymous sign-in](https://docs.unity.com/en-us/authentication/use-anon-sign-in) | 这是在线身份服务能力，不等于本项目要求的纯本地游客档；不要以必须先成功匿名登录替代先玩后绑定。 |
| Unity对已关联其他玩家的身份会返回绑定冲突；强制关联可能使原账号无法恢复。[Unity：Manage linked external identities](https://docs.unity.com/en-us/authentication/identity-management) | 绑定失败不能自动使用force-link解决。玩家选择普通进度，也不等于允许转移认证凭据或丢弃原账号记录。 |
| Unity支持自定义OIDC身份接入，但第三方身份提供方的集成仍需开发者完成；其登录调用可能替换缓存玩家。[Unity：OpenID Connect](https://docs.unity.com/en-us/authentication/openid-connect) | 不能把“支持OIDC”写成已支持微信小游戏或微信登录令牌可直接使用；账号服务边界应与具体SDK分离，并先保存游客来源。 |
| Cloud Save的writeLock不匹配会报告值已改变；省略相应检查可覆盖数据。[Unity：Write locks](https://docs.unity.com/en-us/cloud-save/concepts/write-locks) | 可作为检测并发覆盖的基础能力；它不负责玩家选档、广告依赖核对，也没有由该页证明跨多个业务记录的事务完整性。 |
| Cloud Save的Protected Player Data可由玩家读取、只能由服务端写入；Default允许玩家本人写入。[Unity：Player Data](https://docs.unity.com/en-us/cloud-save/concepts/player-data) | 权益裁定／选档结果应经服务端受控入口，不能开放客户端直接覆盖权威余额。具体权限、容量、事务、部署可达性和成本仍需选型验证。 |

UGS可作为后续候选，不作当前选择；通用账号后端加支持条件提交的存储也可承担同一职责。当前没有证据说明购买某服务就能解决第6节的业务冲突，因此本轮不扩展供应商比价、建账号或部署。跨平台统一的是游戏账号与数据语义，不要求三个客户端具有相同登录SDK。

### 微信小游戏身份：本轮未完成官方条件核实

已尝试读取微信官方的[小游戏UnionID机制](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/union-id.html)、[小游戏登录](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/login.html)、[code2Session](https://developers.weixin.qq.com/minigame/dev/api-backend/open-api/login/auth.code2Session.html)及[移动应用微信登录开发指南](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/WeChat_Login/Development_Guide.html)。网页检索工具未能取得正文；随后浏览器访问UnionID页被站点安全策略明确拦截，未绕过。这些链接是**待核实入口，不是本轮已读取的事实证据**。

因此本研究不保证小游戏每次登录都返回UnionID、不保证当前开放平台／移动应用资质和绑定条件已满足，也不把小程序、腾讯超级App或社区教程的同名接口当作微信小游戏规范。官方条件未能核实是接入设计的已知缺口，不影响先确定游戏账号独立于渠道ID的职责。

后续官方核验必须回答：openid的准确应用作用域；UnionID的开放平台归属与返回前提；小游戏与移动应用能否及如何归入同一开放平台身份范围；Android／iOS移动应用微信登录的接入条件；小游戏临时登录凭证如何由可信后端换取并验证身份、哪些密钥仅能在服务端；用户未产生可关联UnionID时如何通过明确账号登录／双端授权绑定。未经这些证据，不能承诺微信身份自动匹配App账号，也不能将客户端上传的openid／UnionID字符串当作认证证明。

推荐身份边界保留两条路线：官方证明可关联的身份映射，以及用户对已有游戏账号的明确绑定。即使未来证实UnionID可关联，它也只解决“是否同一身份”的一部分，不解决“绑定后选哪份进度”或“两个离线Grant使用如何核对”。
