## 1. 三个讨论层级

| 层级 | 要回答的问题 | 应形成的结果 |

## 2. 当前架构要达到的目标

1. **结果一致。** 战斗、攻略验证、撤销后的重演遵守同一套规则；显示和动画不另算一份结果。
2. **修改有归属。** 重要状态有唯一负责者，其他系统通过明确请求使其变化，不直接越过负责者写数据。
3. **流程能闭合。** 战前、战斗、翻面、救援、结算和退出有明确交接；同一奖励不会多发，已学技能不会因战斗回退丢失。
4. **可以按系统独立工作。** 后续会话知道自己可改什么、依赖什么、必须向其他系统保证什么；新增关卡和职业内容不迫使无关系统同时修改。
5. **外部服务不支配本地战斗。** 网络攻略失败、广告延迟、画面播放速度不能自行改变已经成立的战斗事实。

## 3. QFramework 与业务职责的关系

QFramework 继续作为 Unity 客户端的组织框架。UI、业务流程、状态和平台接入依其分层组织；战斗规则可以由普通 C# 模块承担，再由客户端业务系统调用。规则不依赖画面、输入设备或广告供应商，使游戏与攻略验证能够使用相同规则。

QFramework 的分层不能替项目决定“血量归谁修改”或“奖励由谁统一提交”。这些决定必须在业务架构中明确。下表是**逻辑职责分组**，不是要求每行立刻新建一个 QFramework System，也不是最终类清单；职业、主动技能和被动技能不因名字不同就必须各建一套独立系统。

| 职责分组 | 拥有或负责什么 | 与其他系统的协作约束 |
| --- | --- | --- |
| 角色成长、职业与技能学习 | 长期等级、经验、职业获得、已学技能、阵容与局外恢复 | 提供入场角色资料；实际战斗 HP、CD、状态由当局负责。 |
| 背包与战术装配 | 长期物品与材料数量、合成操作及装配关系 | 读取配置配方，接受合法的学习消耗、装配与结算请求；交给对局使用的同一批物品不能同时在局外再次花费。 |
| 关卡进度与教学 | 开放关卡、首通与教学进度、一次性领取记录、挑战延续关系 | 负责条件与进度判断，应用流程组织赠证和学习，库存与成长各自处理数据；Boss 翻面属于同一战斗，不是第二次关卡通关。 |
| 战斗规则与对局 | 本局敌我状态、行动顺序、技能与道具作用、棋盘状态、面切换条件及战斗结果 | 统一裁定本局结果；接收入场资料和合法操作，向外提供结果；不直接发长期奖励。 |
| 结算协调 | 按规则确定已确认结果的奖励，交给成长、库存和进度处理，确认交接完成 | 成长负责经验积累与升级，各数据仍由其负责系统修改；基础结果与自愿广告增益分别确认，重复请求不能重复入账。 |
| 广告权益 | 已完成广告对应的权益、适用范围和使用状态 | 广告接入只报告完成事实；具体业务判断如何兑现，不由广告回调直接改当前角色 HP 或奖励。 |
| 攻略 | 默认攻略、在线分析请求、结果适用性与内容展示 | 读取局面并复用规则验证；不能改变正在游玩的对局，也不能把旧局面结果认作新局面的保证。 |
| 配置与内容 | 职业、技能、成长、敌人、物品、关卡的规则定义和数值来源 | 提供一致的只读定义；配置中的初始值与正在变化的玩家／战斗状态分开。内容编辑与验证另有职责，使用独立局面生产和验证内容。 |
| 应用流程 | 进入关卡、教学返回、创建或结束对局、调用结算等跨系统步骤 | 协调调用顺序和完成条件，具体规则交回负责系统；不发展成同时计算伤害、管理背包和保存一切的万能模块。 |
| 输入与表现、平台接入、存档 | 分别负责操作意图与显示、广告／网络等外部接入、保存和恢复已确认数据 | 都不取得业务结果的最终裁定权；保存操作不能自行创造新的经验、掉落或战斗结果。 |

## 4. 避免多系统冲突的共同约束

**一项状态由一个明确的负责者修改。** 例如当前战斗 HP 由对局管理，血条只是它的显示。技能、道具与敌人行动可以参与计算，但不能各持有一份互相独立的当前 HP。存档可以保存副本，UI 可以缓存显示，这些副本不能同时成为可独立修改的真实来源。

**区分不同生命周期的状态。** 配置定义、长期玩家进度、当前对局状态、已完成广告事实以及界面状态具有不同的有效期和回退范围。它们可以最终保存在同一份存档中，但不能因为一起保存就一起撤销。长期角色属性与本局属性也有明确的入场交接；局外升级不能无说明地改写一场已经开始的对局。

**请求与结果分开。** UI、教学或广告相关业务可以提出请求，负责系统判断是否合法并给出结果。“申请复活”不等于“已经复活”，“尝试结算”不等于“奖励已到账”。通知已经发生的事实适合供显示、音效等读取；必须有先后顺序的业务交接由明确流程组织，不能依靠多个事件监听者碰巧先后执行。

**裁定分层，协调者也有范围。** 战斗负责本局规则与阶段结果，应用流程负责页面和关卡进出的组织，结算协调负责长期收益交接。技能效果不直接切页面，UI 不直接判胜负，结算不重新打一遍战斗。无需让一个全局状态机同时管理所有角色状态、背包和界面。

**数据依赖有方向。** 输入／表现提出意图并读取结果；业务流程调用各负责模块；可共用规则不依赖 UI、场景、广告或存档。基础 FlowPuzzle 保留几何职责，FightMatch 组合它与战斗规则；攻略使用同一套规则的独立局面，不反过来控制真实战斗。

**跨系统交接必须可判断完成。** 一次开战、学习、结算或权益使用都要能区分未完成和已完成。重试不能重复花费或发奖，中断后不能把部分完成显示为全部成功。具体如何保存、如何重试留给后续系统设计，当前先约定必须保证的结果。

## 5. 用真实场景审查系统间的冲突

这些冲突即使在单线程按顺序执行时也可能出现，关键是修改权限、时间范围和最终裁定是否清楚。

| 跨系统场景 | 容易出现的冲突 | 整体架构必须保证 |
| --- | --- | --- |
| 攻击、技能、DOT、护盾与动画 | 各自扣血或各判一次死亡；动画先播谁就改变结果 | 战斗统一计算实际结果，表现只播放结果；技能内部算法留后续设计。 |
| 清场、补线、Boss 翻面与救援 | 清第一面就结算整关；最终全灭仍要求看广告才能补线 | 战斗给出明确阶段结果，应用流程据此开放正确操作；整关完成后才进入结算。 |
| 成长、学习、广告权益与撤销 | 回退战斗把战前技能、用卡或已看广告一起抹掉 | 战斗回退范围不跨入长期进度和广告完成事实；权益使用按已定规则恢复。 |
| 背包、战斗消耗、退出与救援 | 扣两遍物品；等待救援先返还，继续后又使用同一物品 | 区分长期拥有量和本次携带／剩余量；救援仍是原尝试，真正结束时统一交接且保持数量守恒。 |
| 胜利、经验、掉落、首通与存档 | 重复通知重复发奖，或只保存部分结算 | 结算有统一的完成判断，成长、库存和进度共同形成一次一致的结果。 |
| 广告完成与离开／重开关卡 | 延迟回调误作用于后来打开的另一场战斗；退出丢失已获权益 | 广告事实按原用途接收，兑现时检查适用对象与当前条件，不能盲目修改“当前页面”的对象。 |
| 攻略返回与玩家继续操作 | 已过时的路线覆盖新局面，验证过程修改真实状态 | 攻略与真实对局隔离；应用结果时检查其适用局面，并清楚区分默认参考和当前局面分析。 |
| 配置、客户端与攻略验证 | 对同一行动使用不同技能数值，得出不同答案 | 同一次战斗及其验证／重演使用一致的规则和配置依据；如何打包与导出留后续设计。 |
| 第 16 关教学、地图、成长与背包 | 未满足学习条件就锁住整个游戏；回刷后又恢复旧等级或重复领证 | G01 按已接收规则显示缺口、允许返回旧关、保留长期进度、重进续教；未完成教学只限制该 Boss 的开战。 |

架构是否合理，应通过这些场景能否明确说出“谁接请求、谁裁定、谁改状态、何时交接、失败后保持什么”来判断，不能只看方框是否齐全。
