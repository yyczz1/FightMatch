# FightMatch 多会话执行约定

2026-10-01 · r3 · 配套[五角色组织方案](../docs/architecture/2026-09-30-ai-team-organization.md)。用户已确认“以后就这么执行”；对于已获准任务，按角色分发和回传，不逐包重复询问。实际任务状态以[START_HERE](../START_HERE.md)为准。本日用户新增规则：自动化测试继续优先交dots，代码审查改交GitHub PR Code Review以节省通用Codex额度，详见第7节；不再新建或唤醒本地R做重复代码审查。

## 1. 启用顺序与完成条件

1. **读取现状。** 调度者读 AGENTS、START_HERE、PROJECT_CONTEXT 和组织方案，核对现有未提交工作、活跃任务及暂停边界。完成条件：保留事项、当前角色和本次获准目标有明确记录。
2. **登记负责人。** 五位顶层角色各对应一个实际会话；下层角色按必要任务启用，可接续现有角色。完成条件：登记真实身份、职责、可发送／接收的对象和用户授权出处，旧角色停写时点明确。
3. **交接职责。** 每个会话收到下方启动说明和职责对应的仓库入口，回读范围。完成条件：主责、输入、写入范围、结果路径一致；发现遗漏由负责人修订，日常接包不用再次询问用户。
4. **验证通信。** 先用限定的文档检查任务核对下发、完成事件、正式回执与回收。完成条件：能将具体任务／回合的结果交回指定负责人；工具不支持的路线写明实际替代方式，不假装消息已经送达。
5. **交接测试。** 主测试核现有证据及云环境草稿／发布状态，主程安排必要环境配置。完成条件：执行位置、版本、运行入口、预算、证据路径、结束方式和回传机制明确。该核对不自动启动长测试。
6. **启用获准任务。** 中央从前置已满足的任务中分发，专业负责人按包执行／接收。组织已启用仍不等于产品目标恢复；产品暂停时只执行获准的组织／文档工作。

现行 C 的串行 Unity 责任须在交接包写清切换点；切换前遵守旧合同。每个工作区只有一个 Unity 执行者；独立云环境并行另核资源和许可条件。继续使用外置盘承载本机大型工具／缓存，新增存储位置由具体环境包规定。

## 2. 角色启动说明

每个持久角色使用独立会话。创建时填完整下列说明，不复制整个历史聊天：

> 你在 FightMatch 中担任【角色】。本次实际获准目标是【目标／用户授权出处】。
>
> 先读 AGENTS.md、START_HERE.md、.agent/PROJECT_CONTEXT.md，再读组织方案中本角色职责，以及【本角色输入文件及版本】。
>
> 你的上级／回传对象是【真实 thread／host】；可分发的下级与通信授权来自【用户实际授权及名册】。
>
> 本回合只处理【任务包／版本】，允许读／改／新建的文件、工具、测试和 Git 权限见该包；其余现有成果保留。
>
> 先回读目标、主责、关键决定和范围，再在授权内继续。将详细结果保存到包指定位置，正式回执按本文格式返回。
>
> 如发现范围外变更或缺失前提，只暂停受影响部分，交所属负责人协调，继续独立可做部分。最终结果必须绑定准确输入和证据。
>
> 主产品目标当前为【暂停／明确恢复及范围】；组织分工本身不改变这一状态。

角色专属输入由分发者填写，遵循以下最小范围：

| 角色 | 输入及首项产物 |
| --- | --- |
| 中央 | 项目架构／系统摘要、已定决定索引、里程碑、名册与依赖状态；产出可执行优先序和负责人分配。 |
| 主策 | 策划接续、当前正式规则／配表、相关决定；产出体验及内容子包、验收样例。 |
| 主程 | 架构／系统设计接续、系统目录、共同契约、当前交付；产出架构与系统设计分工、实施和集成次序。 |
| 主美 | 既有美术会话交付、已确认样片、表现需求和平台规格；产出风格／资源清单、样片及制作包。 |
| 主测试 | 验收条件、固定候选、原始证据索引、GitHub审查结果、验证约束；产出差异验证计划、执行申请及审查问题清单。 |
| 下层设计／执行 | 公共入口、上级任务包和相关事实；只产出本包要求的设计、代码、内容、资源或验证。代码审查不再分发给本地R。 |

**模型默认（2026-10-01用户新指示）：** 中央、四位主负责人、架构、系统设计及C等主要会话统一`gpt-6-astra`／`xhigh`（极高），创建和后续分发显式传入，覆盖旧的5.6 Sol／high和C／max默认。明确规则下的重复整理、格式转换、清单核对等小任务可用`gpt-6-luna`／`low`；遇到歧义、设计判断、重要代码修改则交Astra。旧R不因改模型被唤醒做审查，GitHub审查仍用服务实际配置。切换不追溯改变已运行回合；登记请求值与已实际生效的回合，不能把当前在途推理写成已换模型。

## 3. 角色与任务登记

中央维护一个角色登记入口；每位负责人维护本线任务索引，子会话只写指定报告，避免所有人同时编辑同一张表。启用时在具体包中指定登记文件和唯一维护者。

角色登记至少含：

```text
角色／职责：
实际 thread／host：
状态：待启用／活跃／交接／结束
模型／运行环境：
上级与允许通信对象：
用户授权出处：
当前任务／实际回合：
输入版本／允许写入范围：
结果路径：
前任角色／停写时点：
```

会话状态与任务状态分开。任务记录“草案 → 可执行 → 执行中 → 待专业接收／验证 → 已接收”；失败后记录“待修正”并链接纠正包，真实前置缺失记录“受阻”。程序／资源包必须经过其规定的验证门；纯文档包按文档验收，不为填流程强跑 Unity。

收到别的会话消息不自动扩大通信授权。名册依据用户真实许可填写；工具不支持跨会话主动回复时，由授权调度者接回指定回合并转交正式摘要。不得把一封收到的任务消息自行解释为用户授权所有相互通信。

## 4. 任务包

沿用[既有任务包模板](TASK_PACKET_TEMPLATE.md)的白名单、受保护变更、验收、验证和 Git 权限字段；Codex 内部任务使用其字段，不机械复制外部 DeepSeek 的人工传递步骤。加入以下协调字段：

```text
任务ID／修订：
唯一交付负责人／设计方／执行方／专业接收方：
独立审查方（代码为GitHub PR Code Review；记录PR/base/head）：
用户目标及已定决定：引用具体路径／章节
输入：源码提交或不可变快照、配置／资源版本、相关设计版本
前置任务：哪些必须已接收，哪些可并行
交付物：精确文件及格式
允许读／改／新建：逐项路径；共享文件的唯一写入者
验收：逐项可观察结果，含相关失败／中断场景
执行／验证：准确入口、运行位置、次数与耗时预算、停止条件
返回：报告路径、接收 thread／host、任务／回合对应
权限：创建／消息／工具／Git／费用分别引用实际授权
```

框架、依赖、公共接口、序列化、资源规格或规则需改变时，先形成变更提案：原决定、必要原因、影响范围、具体替代、验收变化。负责人在既有授权内处理普通技术问题；改变用户决定或引入新承诺，由中央集中提交具体方案。不能在交付后把自行变更写成既定事实。

## 5. 测试申请与回执

主测试先判断原证据覆盖什么、新改动需要补什么，再出验证计划。一次运行应回答明确问题，禁止按角色数量重复整套测试。

测试申请：

```text
测试申请ID／来源任务／负责人：
固定输入：提交或快照哈希、配置／资源／安装包身份
验收条件与风险场景：
已有证据：路径、对应版本、可复用范围
需要补证的变化：
执行环境／准确入口／预计及上限耗时：
结果与日志路径：
前置／本次结果阻塞的任务：
完成回传对象：
```

执行回执：

```text
任务／申请ID、准确 thread／host／turn：
执行位置与工具版本：
输入身份／实际运行范围：
逐项结果：通过／失败／未验证，附对应证据路径
退出状态、用例数、失败／跳过数及耗时：
缺陷或环境故障：复现、影响、推荐交回负责人
是否修改过输入／断言：列实际变更
下一步：需要修正或已可交接的条件
```

主测试核对实际日志／结果与输入身份，接收对应PR/head的独立审查结果，再给ACCEPT／NEEDS_FIX／REJECT接收结论。作者自检、测试完成、GitHub审查结果和最终验收是不同事实；不把机器人原始答复改写成它未给出的批准。缺少设备／视觉证据时保持该项未验证。

## 6. 回传与继续推进

1. 每个任务只登记一个完成接收者；其余角色不重复等待或转报。沿人类已授权通信路线由执行者在完成时回传，接收者必要时才做一次有界等待／拉取。没有独立可做事项的角色结束回合，按需唤醒，不循环等待上级。
2. 接收者核对交付范围、固定输入、各验收项与原始证据。需要修正时只下发具体纠正包；结果回来后，不重复整个上游设计。
3. 接收结论回到任务负责人。负责人更新本线索引，向中央发送“任务状态、影响的依赖、下一可做事项、需要用户决定的具体问题、证据链接”。
4. 中央据依赖图继续分配可执行任务。测试等待只阻塞依赖该结论的验收／发布；不冲突的设计、内容和资源工作可继续。
5. 普通技术问题交专业负责人处理。只有确需用户选择／手动操作时，先完成独立部分，再集中说明原因与可评审方案。

中央不需要常驻完整日志；暂停、恢复、需求修订和正式接收通过仓库索引传播。角色换会话时先落交接，再按真实身份接续，避免新旧会话同时维护同一文件。

节省token优先：中央唯一维护[短接续快照](../docs/team/2026-09-30/README.md)，只在候选、状态、下一动作或阻塞真实变化时更新；历史和细节按链接定位，不整篇重读。小包可由中央转交已经准备好的执行合同，无需主程／主测试各转发一次。回执限结果、改变的依赖、证据位置和确需决定的问题；哈希、白名单、计数、格式用脚本核对，必要修正合并派发。已有测试及失败不因流程调整重跑；下一项实际小交付只做一次按回合计的响应数与输入／缓存／输出token对照，不能将累计输入当账单。角色数按实际可并行工作收缩，不让组织图变成每包必须经过的层级。

## 7. GitHub PR Code Review

本节覆盖旧任务包中尚未执行的本地R代码审查门；已有回执与失败证据保留。纯方案、策划及美术的专业接收仍由对应负责人完成，不为改审查入口重跑测试。

1. 主程固定一个连贯变更的源码、设计和现有验证证据。中央在无活动写入／验证冲突时，按实际Git授权保存到`codex/`审查分支并开PR；未完成验证时明确标为草稿及列出缺项，不能当已验收版本直接进入master。
2. PR说明具体行为、范围、验收条件、相关设计及通过／失败／未运行的证据，记录base与head。只提交所需文件，不带凭据、本机权限、缓存或真实玩家存档。把PR附加到当前任务。
3. 使用仓库已启用的自动审查；未自动触发时，在PR评论一次`@codex review`。记录触发与完成链接。不要同时派本地R、`/review`或第二个代理复审同一代码。
4. 主测试接回GitHub原始结论，核对实际审查head，汇总问题交原执行者。无评论、仅排队／👀、额度不足、连接失败均不是通过；已完成且无发现的结果只关闭代码审查门，不关闭测试／设备门。官方当前说明GitHub审查聚焦P0/P1，不据此宣称所有级别问题均不存在。
5. 有问题只修相应范围；代码变化后按影响补验证并请求对应新head的审查。复用仍有效的证据，不因PR描述或日志补全机械重跑整套测试。主测试记录最终接收结论和未完成项，中央继续下一就绪包。
6. 集成未启用或权限／额度受阻时，先完成PR及独立可做部分，再报告所需人工操作；不得自行改用消耗通用额度的审查会话或购买额度。推送审查分支不等于批准合并、部署或发布。

用量口径：GitHub触发的Codex审查计入Code Review用量；本地或GitHub外审查计入通用用量。不是无限免费服务，具体额度以账号显示为准。[官方用量说明](https://learn.chatgpt.com/docs/pricing)、[GitHub审查设置与触发](https://learn.chatgpt.com/docs/third-party/github)。
