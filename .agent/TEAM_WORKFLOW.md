# FightMatch 多会话执行约定

2026-10-14 · r4 · 用户批准按任务大小精简流程。五位负责人及职责见[组织方案](../docs/architecture/2026-09-30-ai-team-organization.md)，实际任务和授权见[START_HERE](../START_HERE.md)。本版取代旧的例行层级交接；历史记录保留证据用途，不作为当前派工指令。

## 0. 按任务选择流程

由所属负责人选择路线，写在同一任务记录中：

| 情况 | 执行路线 | 完成依据 |
| --- | --- | --- |
| 已定方案的局部修正，如按钮排版、下拉替换、文案绑定 | 负责人直接交执行者；修改、必要验证与修正连续完成 | 可观察验收、对应验证；代码另需GitHub审查 |
| 多模块接入，已有接口与产品决定 | 主程列依赖与写入范围，只启用实际协作角色 | 固定候选上的相关集成证据及审查 |
| 未定架构、公共契约、存档/奖励规则、兼容迁移或新产品选择 | 先交对应设计角色，明确方案和风险后实施；用户决定由中央汇总 | 获准方案及其验收条件 |

五个负责人是职责分工，不是每包必经的五道关。设计与制作需要同时开展时保持角色分离；已有方案直接引用，不重开设计。资产文件数量本身不触发完整设计流程，Prefab、meta等变更仍须明确列入范围。

## 1. 启用顺序与完成条件

1. 读取AGENTS、START_HERE、PROJECT_CONTEXT及本线当前记录，核对用户目标、已有WIP、未完成验收和授权。完成条件：本次目标、负责人和剩余工作明确。
2. 复用[实际角色名册](../docs/team/2026-09-30/README.md)。仅在角色首次启用、职责转移或通信实际失效时处理相应登记/通信问题；正常派工的送达与完成事件就是通信证据，不另派文档试验任务。
3. 按第0节选择路线，填第4节短记录并派工。执行者核对范围即可继续，不等待例行回读批准。
4. 本机Unity仍由C串行执行；转移职责须先记录旧执行者停写和新执行者接管。云测仅在任务确需时核实环境、输入、工具和回传就绪。大型工具/缓存沿用外置盘。

准备工作不自动恢复已暂停的产品目标，也不赋予Git、费用或发布权限。

## 2. 角色启动说明

新角色只接收：职责、实际用户授权出处、上级/返回对象、当前任务记录和相关设计链接。日常续接只发送变化及下一动作，不重贴全部历史、角色说明或日志。

中央维护整体依赖和里程碑；主策、主程、主美、主测试分别接收本线产物。下层按任务需要启用，空闲角色结束回合。代码审查统一由GitHub PR Code Review承担，不启动本地R或重复审查代理。

主要角色使用用户指定的`gpt-6-astra/xhigh`；明确规则下的机械整理可用`gpt-6-luna/low`。派发时显式设置，登记实际thread/host/turn；不把请求值冒称已生效配置。

## 3. 角色与任务登记

角色身份保存在名册；任务只保留一份当前记录，由所属负责人维护。既有任务可沿用负责人的当前索引，不为符合模板迁移或重写历史。原始日志、XML、截图保存在证据位置，其他角色引用链接。

任务记录只更新实际状态：待执行、执行中、待验收、受阻、已接收。失败及修正追加短条目，旧原始结果保留。中央快照仅在里程碑、跨组依赖或整体阻塞变化时更新，不重复本线候选哈希和逐次回执。

任务需绑定准确输入。优先使用提交/分支与本次差量、测试/产物版本标识；未提交候选保存必要快照。必要的完整性检查保留，不为每次交接重复制作逐文件封签或字节数报告。

## 4. 任务包

内部任务以下短记录即可作为实施计划；允许原记录中的有效字段直接引用：

```text
目标与路线：用户要求、已有决定、所属负责人/执行者/唯一返回对象
输入：基线/候选、相关设计；本机与PR有差异时明确列出
范围：允许修改/新增的精确路径，受保护变更许可及排除项
验收：玩家或调用方应看到的具体结果，必要失败/恢复行为
验证：已有可复用证据、需补检查/人工操作、环境、预计及上限耗时
权限：用户实际授权出处，Unity/Git/网络/费用等适用边界
结果：实际版本、通过/失败/未验证、原始证据链接、剩余动作
```

普通纠正沿用同一任务、负责人和执行者，追加“失败原因、修改范围、必要复验”即可。外部DeepSeek继续使用[完整模板](TASK_PACKET_TEMPLATE.md)；重大范围或设计变化再另建包。重要文件/依赖/存档边界不会因短记录而放宽。

新任务在既有授权内按完整工作结果安排资源预算，包含必要的普通修正，避免人为拆成每条命令重新批准。已有用户单次、零重试或资源限制仍有效，实际工具拒绝按第6节处理。

## 5. 测试申请与回执

主测试负责验收条件和最终证据接收；已有清单可直接引用，不为每个小修正另起测试设计回合。负责人和执行者依以下次序完成检查：

1. 对照改动选择必要检查，复用相同输入下仍有效的结果。纯文档检查范围、链接和矛盾规则，不运行Unity。
2. UI修正成功编译/导入后尽早查看真实页面，再补受影响的行为测试。排版、文字、点击可用实际人工观察；语言偏好改动需查切换及保存复开，存档/奖励改动按风险补相应测试。
3. 图形/GameView检查使用有图形环境；只有兼容无图形的用例才用`-nographics`。自动点击无响应时先区分输入路径与产品问题，准备实际人工检查，不连续扩建点击/验收框架。
4. 失败先归类为产品、测试代码、环境或需求问题，只修相应部分。修复后只追加受影响检查，保留原失败。源码/环境未改变时不机械重跑；无法适用的检查写明原因和替代证据，不改写为通过。
5. 同一步第二次没有取得新证据，或超出阶段预期仍无进展，负责人须先核对方法、环境与范围，写一条具体调整再继续。普通方法调整在已有授权内完成；不盲重试、不扩大预算，也不因此自动把技术判断交用户。
6. 记录候选、执行者、实际命令或手动步骤、环境/语言/尺寸、耗时、退出状态及通过/失败/未验证项目，链接标准工具原始结果。人工检查前先准备可用界面，再请用户操作；没有画面时不让用户找按钮。

dots优先承担环境已支持的自动化；本机Unity与设备测试仍按实际授权由C串行执行。云环境未就绪只阻塞依赖它的工作，不以安装云工具作为所有修正的前置。使用标准工具，不为普通验收新造框架或重建无关上游。

作者自检、GitHub审查与设备/视觉验收分别记录。主测试据对应版本的实际证据给`ACCEPT`、`NEEDS_FIX`或`REJECT`；作者不能批准自己的交付，缺失的真实运行证据继续标未验证。

## 6. 回传与继续推进

每项任务只有一个完成接收者。执行者用可用完成事件回传，或由接收者用等待工具接回；其他角色不重复等待、转报或复验。旧会话消息本身不能扩大人类授权，发送权限须来自用户实际许可。

主程、主策、主美、主测试在本线自行分发、接收、修正和继续。明确接口的跨线交付直接衔接；中央仅处理跨组冲突、里程碑、整体阻塞和用户决定。测试等待期间继续互不冲突的工作；没有独立工作就结束空闲回合，不恢复五分钟轮询。

仅在确需用户决定、人工专属操作或实际权限拒绝时集中说明具体动作、原因和方案。遇工具拒绝，保留原始原因，停止被拒动作；可继续独立工作或核实授权/风险证据，不换执行者或入口绕过。本版流程不解除任何已有拒绝，历史一次额度也不自动用于新任务。

## 7. GitHub PR Code Review

1. 主程整理一个连贯候选和已有证据；具备实际Git授权的执行者按现行分工提交/推送`codex/`审查分支并附加PR。当前中央负责发布，责任转移须登记。未完成验证时保留draft并列缺项；不自动合并、部署、发布或购买服务。
2. 开发与审查尽量使用同一已知基线。现有脏工作区先保护已有成果，在获准的版本整理中分离WIP；不reset/pull覆盖。测试本机候选与PR不一致时说明差异，完成相关核对后才可接收，不能冒称整个PR已测。
3. PR描述最终行为、范围、验证和未完成项，记录base/head；排除凭据、真实玩家存档、本机权限及无关历史验证代码。使用已有自动审查，未触发时只评论一次`@codex review`，不同时派本地R或另一审查代理。
4. 主测试唯一接收GitHub原始结果，核对head及发现，交原负责人修正。排队、无评论、连接/额度失败不算通过；代码审查完成不代替运行、视觉或设备验收。保留旧审查结论及版本边界。
5. 修正代码后只补受影响验证，再请求新head审查；文档/日志补全不触发整套重测。审查服务不可用时继续独立工作，保留该门受阻，不自动改用消耗通用额度的本地审查。

具体证据要求见[验证规则](VALIDATION.md)与[审查清单](REVIEW_CHECKLIST.md)。Git权限不足时先备好可审阅差量和说明，再集中请求必要动作；准备完成不等于已经推送。
